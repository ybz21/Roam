Roam · Web · 19 · 改进方向

目标架构与数据分层设计

← 问题

问题篇查清了四条病根：普通会话不落盘、 sessions 拿 $N 当主键、项目按「此刻有没有会话」退场、$N 跨重启复用串档。 本篇给最终状态：改完之后数据长什么样、分几层、谁是真相源，以及重启恢复怎么走通。

1. 最终状态与目标架构

一句话：台账进一个库，配置留文件，大对象留盘，tmux 只回答「现在谁活着」。

  • 一个真相源，一套库：项目、会话、归属、父子、竞赛、蜂群全在 meta.db， 有 schema 版本、有事务、有外键。ttmux 层与 Roam 层不再是两套存储 —— 「两层」改完之后只是代码归属，不是存储边界。唯一保留的划分是 每张表一个写者（会话类归 CLI、项目类归后端，见 §8.1）， 那是为了不让两个进程抢同一批行，不是把层分回来。
  • 台账不随 tmux 生死：主键是持久会话 id（含创建时刻，跨重启唯一）， $N 降级成一列运行时句柄。会话死了置 dead 不删行。
  • 项目不因「此刻没会话」消失：退场判「从来没有过会话」，干过活的转归档。
  • 重启后可恢复到三级：台账在 → 历史在 → 能一键重开（连带接回 agent 对话）。
台账（真相源） 配置 运行时（易失） 大对象 / 派生 / 第三方
和现在的差别就两处，但都是根上的： ① 写入口从「各写各的 JSON / 各开各的 sqlite 连接」收成一个 internal/metadb； ② tmux 从「台账的一部分」降级成「一列可对账的运行时状态」。 其余（配置留 JSON、日志留文件）保持不变 —— 它们本来就存对了地方。

2. 数据分层设计：台账 / 配置 / 大对象

病根之一是「所有持久化都被当成同一件事」，于是台账用了改一个字段就全量重写的 JSON， 而会话历史被交给 tmux 保管。三类数据的要求完全不同，存法也该不同：

类别特征存法例子
台账有关系、要事务、要按条件查、会长期累积SQLite meta.db，带 schema 版本与迁移项目、会话、归属、父子、竞赛、蜂群
配置单写者、无关系、人手要能改、量小JSON 文件，保持现状偏好、浏览器/手机/语音配置、导航站、TOTP
大对象只追加、体量大（本机 38MB 日志）、按 id 直取文件系统，DB 里只存索引logs/<id>.log、对话 transcript

另有一条正交的划分——什么是真相源，什么是现算的：

  • 台账（持久）：项目、会话、归属、父子、竞赛、蜂群 —— 存 meta.db。
  • 运行时（一次 tmux server 生命）：谁 attach、activity、pane 尺寸、$N —— 只问 tmux，不入库。
  • 派生（一次请求）：git 状态、worktree 列表、pane 内容、waiting 判定 —— 现算，入库只会不一致。
现在的错误在于把台账的一部分（会话是否存在过）交给了运行时层保管。 tmux 只该回答「现在谁活着」，不该回答「有过什么」。

3. 目标 schema

单库 <dataDir>/meta.db，schema_meta 管版本，迁移脚本放 cli/ttmux-cli-go/internal/metadb/migrations/。

这一节是 M2 的目标 schema，不是现在的表结构。现在只有 sessions 一张表 按这个方向改到位了（主键换持久 id，加 status / died_at / died_reason / tmux_id / tmux_epoch）； projects 仍是 projects.json（只多了 lastSessionAt 一个字段）， tmux_epochs / project_aliases / archived_at / spawn_cmd / restored_from 都还没有。逐项状态见 §9。

3.1 DDL

CREATE TABLE schema_meta (version INTEGER NOT NULL);

-- tmux server 代次：server pid，随 server 起落而变。
-- 用来把「你手动 kill 了会话」和「机器重启把整个 server 带走了」分开记。
CREATE TABLE tmux_epochs (
  epoch      TEXT PRIMARY KEY,
  started_at INTEGER NOT NULL,
  seen_at    INTEGER NOT NULL
);

CREATE TABLE projects (
  id              TEXT PRIMARY KEY,          -- 沿用现有不可变 id，老链接不失效
  dir             TEXT NOT NULL UNIQUE,
  origin          TEXT NOT NULL DEFAULT '',  -- '' = discovered | 'user'
  display_name    TEXT,
  pinned          INTEGER NOT NULL DEFAULT 0,
  default_agent   TEXT,
  default_base    TEXT,
  first_seen      INTEGER NOT NULL,
  last_seen       INTEGER NOT NULL,
  last_session_at INTEGER NOT NULL DEFAULT 0,  -- 最后一次有会话的时刻
  archived_at     INTEGER                     -- 软退场，NULL = 在册
);
CREATE TABLE project_aliases (alias TEXT PRIMARY KEY, project_id TEXT NOT NULL);

-- 主键是**持久会话 id**（= tmux 会话名，见 docs/design/session-identity.md）：
-- 由创建时刻派生、不可变、跨 tmux server 重启唯一且永不复用 —— 天生就是对的主键。
CREATE TABLE sessions (
  id           TEXT PRIMARY KEY,
  label        TEXT,                      -- 展示名快照（会话死后 @roam_name 就没了）
  parent_id    TEXT REFERENCES sessions(id),
  project_id   TEXT REFERENCES projects(id),
  home_dir     TEXT,                      -- 归属目录（吸收 session-homes.json）
  worktree_dir TEXT,
  agent        TEXT,                      -- claude | codex | shell | …
  kind         TEXT,                      -- task | swarm-member | race | plugin | plain
  created_by   TEXT,
  created_at   INTEGER NOT NULL,
  spawn_cmd    TEXT,                      -- 重开所需的全部输入（§7）
  spawn_env    TEXT,                      -- JSON
  status       TEXT NOT NULL DEFAULT 'live',  -- live | dead
  died_at      INTEGER,
  died_reason   TEXT,                      -- killed | host-restart | unknown
  restored_from TEXT REFERENCES sessions(id),
  tmux_id      TEXT,                      -- 运行时句柄，只在 status=live 时有意义
  tmux_epoch   TEXT REFERENCES tmux_epochs(epoch)
);
CREATE INDEX sessions_project ON sessions(project_id, status);
CREATE UNIQUE INDEX sessions_handle ON sessions(tmux_epoch, tmux_id)
  WHERE tmux_epoch IS NOT NULL;
为什么主键必须换成持久会话 id。session-identity.md 已经把会话 id 定义成 id.ForSession(session_created, session_id) —— 它包含创建时刻，所以重启后新会话 拿到 $0 也撞不上旧会话。台账早就有一个跨重启唯一的键，只是没拿它当主键。换过来之后： 重启不再是「主键全部失效」，只是 tmux_id 置空；$N 复用天然无害， 因为 (epoch, tmux_id) 才是句柄；死会话的行可以安然留着，它的主键不依赖任何活着的东西。

4. 项目生命周期：退场判「有没有过」，不判「此刻有没有」

现在（M1 已落地）
目录不存在                                     → 硬退场
origin='user' 或 pinned                        → 永不退场
roamWts=0 ∧ 活会话=0 ∧ 历史会话=0 ∧ 无竞赛/蜂群 → 退场
roamWts=0 ∧ 活会话=0 ∧ 历史会话>0              → 不删，留在正常列表里

M3 目标
最后一条改成 → archived_at=now，项目页收进「不活跃」分组、默认折叠
归档态目前只是设计，代码里还没有。Entry 现在只有 LastSessionAt （backend/project/service.go），聚合层据此不删这类项目，但它们和活跃项目 混在同一份列表里，没有「不活跃」分组、没有折叠、也没有 archived_at 字段。 archived_at 出现在 §3 的目标 schema 与本图的虚线框里，属于 M3。

5. 会话生命周期：软删，不硬删

Reconcile(alive, epoch)
  对每行 status='live'：
    命中活会话                    → 刷新 label / tmux_id / tmux_epoch
    未命中，且 tmux_epoch = 当前   → status='dead', died_reason='killed'
    未命中，且 tmux_epoch ≠ 当前   → status='dead', died_reason='host-restart'
  对每行 status='dead' 且会话名又活了：
                                  → 复活成一行干净的 live 记录（不继承旧来历）
  tmux 盲态                        → 一行都不动

一行都不 DELETE。清理另起一条低频路径：status='dead' ∧ died_at 早于保留期（默认 90 天）
∧ 不属于任何未收尾的 worktree/竞赛/蜂群 → 删除，并连带删 logs/<id>.log。
条数上限默认 5000。

6. 重启恢复链路

不做什么。不做会话内容/进程的恢复 —— pane 里的 agent 进程死了就是死了， 恢复的是会话这个壳（同目录、同 agent、同 label、同 worktree 绑定），不是现场。 也不默认自动拉起：重启后自动跑起十几个 agent 是危险动作。

7. 重开（restore），不是自动恢复

sessions 存了 home_dir / worktree_dir / agent / label / spawn_cmd / spawn_env，足够把壳原样重建。

  • 手动重开：会话列表 / 项目详情页里，dead 会话行末给一个「重开」动作 → POST /sessions/:id/restore → 走现有 ttmux new --json 建新会话（新 id）， restored_from 指向旧行，归属与 label 照抄。旧行保持 dead，不复活。 重开的是壳；agent 的上下文由 agent 自己的 resume 机制负责，我们不假装能接上。
  • 开机恢复：设置页三档 —— 关（默认）/ 仅置顶会话 / 全部。 默认关的理由写在设置项说明里。
  • 恢复哪些：只考虑 died_reason='host-restart' 的行，且按项目去重上限（每项目 ≤3）， 免得一次重启拉起几十个 pane 把机器再压死一次。

7.1 对话（agent transcript）怎么接回来

Claude Code 的对话存在 ~/.claude/projects/<cwd-slug>/<uuid>.jsonl， 与 tmux 无关，重启一段不丢（本机 1.1GB / 166 段）。缺的只是「Roam 不认识它」。 补上一列即可：会话表记下 agent_session_uuid，重开时 claude --resume <uuid>，界面上就能从「已结束的会话」直接接回原对话。

这是把 ①台账 → ③重开 真正闭环的一步：没有它，重开只能给你一个空壳； 有了它，重开等于把那天下午的活原样接着干。

8. 一套库：写者、直连与迁移

8.1 一套库，不分层——但要分「谁写哪张表」

ttmux 层和 Roam 层不再各存各的，物理上就是一个 meta.db、一套 schema、一套迁移。 「两层」在改完之后只是代码归属，不再是存储边界 —— 问题篇里那张「一个目录两套机制」的图， 到这里就作废了。

但有一件事不能跟着一起取消：每张表只有一个写者。两个进程写同一个 SQLite， WAL 能让读写并发，写本身仍然是串行的；真正省掉锁竞争的不是 WAL，是「不会有两个进程同时想改同一批行」。 这不是把层分回来，是按数据的归属分：

表写者另一边怎么办为什么
sessions · tmux_epochsttmux CLI后端只读；要写就调 ttmux 子命令会话 id 的唯一出处在 CLI，编排逻辑也在 CLI（「薄封装」原则）
swarms · swarm_membersttmux CLI同上蜂群编排整个在 CLI
plugin_sessions · plugin_findingsttmux CLI同上插件宿主在 CLI
projects · project_aliasesRoam 后端CLI 不碰项目是 Web 侧的概念，CLI 里没有
racesRoam 后端CLI 不碰竞赛只有 Web 有入口
唯一的跨写者动作是「建会话时顺手 touch 项目」。它现在也不是一个事务 —— CLI 建会话、后端下一轮轮询时才把项目记上。并库之后可以合成一个事务， 但那要求 CLI 也能写 projects，就破了上面的单写者。 建议维持现状：项目台账本来就是「读时收敛的读模型」，晚一轮记上没有任何影响， 不值得为它引入双写。

8.2 后端要不要直连这个库

一个容易被忽略的实情：后端现在连 sqlite 依赖都没有（backend/go.mod 里没有 modernc.org/sqlite），它对 meta.db 完全不知情，所有访问都是 exec 一次 ttmux ... --json。所以「一套库」落地时有个明确的岔路：

方案代价收益
全走 CLI（不加依赖）项目页要会话历史 → 每个项目 exec 一次，退化成 N 次进程启动架构最一致，后端零 DB 知识
只读直连 + 写走 CLI后端多一个 sqlite 依赖，且必须守住上表的写者约定问题篇 §5 那条跨层长链换成一次 JOIN
选后者。并库的全部意义就在于「项目卡上能直接显示会话历史」—— 如果读还是一次一次 exec，那张表并不并在一起没有区别。 写仍然走 CLI，所以「薄封装」原则一点没破：后端不重实现任何编排逻辑，它只是换了一种更便宜的读法。

8.3 一个该留在外面的例外：蜂群 posts

「一套库」有一处值得破例。每个蜂群现在有自己的 swarms/<群>/swarm.db， 里面是 members / cards / posts：

  • members / cards 并进主库 —— 它们要和 sessions join （成员会话死了还得找回它的日志），正是并库要解决的问题；
  • posts 留在每群自己的库 —— 它是广场聊天流，是全系统写得最频繁的表， 并进主库只会让主库的写锁竞争明显变差；而且「删掉一个蜂群」现在是删一个目录， 并进去之后要变成一串带外键的 DELETE。
判据不是「它属于哪一层」，而是写入频率和生命周期： 需要跨实体 join 的进主库，只在自己生命周期内高频追加的留在旁边。 这和 §2 把日志、transcript 留在文件系统是同一条原则。

8.4 连接层

  • PRAGMA journal_mode=WAL、busy_timeout=5000、foreign_keys=ON；
  • 进程内单例 *sql.DB；单写者内部的多表写走一个事务（建会话 = 写 sessions + 记 tmux_epochs）；
  • 统一放进新包 internal/metadb，sessmeta / swarm / plugin 都改用它； 后端用同一个包的只读入口。
CLI 必须能独立工作。库的位置、建库、迁移全部由 CLI 负责 —— 后端没起、甚至没装， ttmux 也要照常能用。所以「一套库」的落点是 <dataDir>/meta.db（CLI 的地盘）， 后端是接进来的那一方，不是反过来。

8.5 迁移

一次性、幂等（标记 migrations/metadb-v3.done）。只增不减：任何一步认不出来的数据，宁可留成一行 dead 记录，也不丢。

来源去向认不出来的行
projects.jsonprojects + project_aliases原文件改名 .bak-<时间>
session-homes.jsonsessions.home_dir按 $N 认不到会话的，用 name 快照回填成 dead 行
meta/<id>/*.txtsessions 的 kind / home_dir / created_at目录保留（CLI 老路径还在读）
races.jsonraces—
swarms/<群>/swarm.db 的 members / cardsswarm_members / swarm_cardsposts 原地不动（§8.3）
老 sessions 表v1 主键就是会话名，直搬；v2 按 name 列重建主键，parent 的 $N 用同表内映射翻译解析不出的落成 dead 行，先整库备份
v2 迁移不再依赖 tmux是关键改动。老迁移要先问 tmux 要「名字 → $N」才肯搬， tmux 一死就整批丢弃 —— 这正是重启后历史被清空的第二重原因。 现在用同表内的 id → name 映射翻译 parent，tmux 死透了也搬得动。
