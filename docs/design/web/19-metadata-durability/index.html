元数据存储：现状与病根

改进方向 →

机器重启后打开 Roam：项目卡全空、会话一个不剩、翻不到任何历史。这不是「重启当然会丢」—— tmux 会话死掉是必然，但「这个会话存在过、在哪个目录、干过什么、日志在哪」是用户数据， 不该跟着 tmux 一起消失。

本篇只做一件事：把数据现在存在哪、为什么一重启就没，查清楚说明白。 所有结论都带本机实测。改法在改进方向那篇。

结论先放这：最要命的不是「数据被删了」，而是绝大多数会话从来没往盘上写过任何东西。 写日志（pipe-pane）只在蜂群成员、任务会话、插件会话三条路径上设置； 日常的 ttmux new 和 Web「新建会话」建出来的会话，在 Roam 主目录里一个字节都不留。

1. 现状：两层，一个目录，两套互不认识的存储

ttmux 层（Go CLI，编排 tmux）和 Roam 层（Web 后端，Gin）共用同一个主目录 ~/.roam（ROAM_HOME 可覆盖），但用的是两套完全不同的机制： ttmux 层有一个 SQLite（meta.db），Roam 层是一堆各写各的散装 JSON。 两边谁也不读谁的表。

ttmux 层 Roam 层 运行时（易失） 第三方存储

2. 项目存储（Roam 层）

项目整个活在 Roam 层：ttmux 层不知道「项目」这个概念，它只管会话。 项目台账现在是 <dataDir>/projects.json —— 一个改一个字段就全量重写的 JSON，没有事务、没有版本号、没有任何外键把它和会话连起来。

2.1 项目是读模型，不是用户建的对象

这是理解它为什么会「重启后全没」的关键：项目主要不是用户创建出来的，是被发现的。 聚合层每轮把会话的归属目录 join 成仓库根，join 到谁就 Touch 谁 —— 入册是「看见会话」的副作用。于是两条入册通道：

通道怎么进来的字段能否自动退场
discovered会话归属目录 join 命中 → Touch(dir)origin=''能 —— 这就是重启后全灭的那批
user用户显式 POST /projects（项目 = 任意目录，不与 git 绑定）origin='user'不能，只能显式 DELETE
本机实测：台账里 discovered = 0 个，13 个全是 origin=user。 不是用户从来没在别的仓库里开过会话，是发现来的那些已经被历次重启清干净了—— 「发现」通道的产出，被「此刻没会话」的退场规则一轮一轮吃掉。

2.2 身份是不可变 id，目录只是可变属性

早期版本拿「目录名 slug + 路径 hash」当 key，mv 一下项目目录身份就变、 置顶和显示名得靠合并搬家。现在 id 入册时生成、永不改，dir 只是一个字段： 

项目 id   2026-0728-1202-30xe      // 不可变，一切 URL / 偏好 / 书签的 handle
dir       /home/ai/codes/ttmux     // 可变属性：mv 目录、worktree 子目录归位仓库根，都只改这里
aliases   老 key → 现行 id          // v1 的 hash key、被合并掉的 id 都记在这，老链接不失效

SetDir(key, newDir) 两种走向：
  newDir 没被占用        → 改 dir，id 不变，偏好一个不丢
  newDir 已有别的条目     → mergeInto 合并（置顶/显示名/最早 firstSeen 取「用户意志」的并集），
                          旧 id 落进 aliases，指向旧 id 的别名一起改指

自愈也挂在这条路上：聚合时若发现条目的 dir 指向的是仓库子目录 （历史脏数据或瞬时误判），用 ResolveRepo 归位到仓库根 —— id 不变， 所以置顶、显示名、默认 agent、老链接全都不动。

2.3 存了什么

字段含义丢了会怎样
id不可变身份所有 #/projects/<id> 链接失效
dircanonical 目录（git 项目 = 主仓库根）条目等于没有

lastSessionAt最后一次有会话的时刻 —— 退场判据看它退场规则退回「此刻有没有会话」，重启即全灭

另有一份不是真相源的旁证：activity.log（JSONL，只增不改，超 5MB 轮转一代）。 它记「任务 → 动作（merged / discarded / cleaned）→ 统计」的摘要，用来在 worktree 删除后 还能追溯「这个任务去哪了」。丢了只损失摘要，不影响任何判定。

3. 会话存储（ttmux 层）

会话整个活在 ttmux 层：Roam 层不生成会话 id、也不直接写会话台账，它调 ttmux new --json，id 的唯一出处在 CLI。问题是——写不写盘，取决于会话是怎么建的。 同样是一个 tmux 会话，走不同入口，留在盘上的东西差了三个数量级：

建会话的入口sessmeta 行输出日志任务描述代码
任务会话 ttmux spawn有有 pipe-panemeta/<id>/*.txtspawn/spawn.go
蜂群成员有有 pipe-paneswarm.db membersswarm/members.go
插件会话有有 pipe-paneplugin_sessionsplugin/hostapi.go
fork 子会话有无无session/fork.go
ttmux new / Web「新建会话」无无无runtime.CreateSession
最后一行就是你每天用的那个入口。它建出来的会话在 ~/.roam 里彻底隐形： 既没有 sessions 行，也没有 logs/<id>.log，连「它存在过」都无从证明。 下一节 §4.1 是这条的实测。

3.1 会话 id 本身是好的

值得说清楚的是：会话的身份设计没问题，出问题的是台账拿什么当主键。 会话 id（2026-0812-1740-0000）由 id.ForSession(session_created, session_id) 派生， 包含创建时刻，因此不可变、跨 tmux server 重启唯一且永不复用 —— 它天生就是一个可以跨重启用的键。台账早就有这个键，只是没拿它当主键（§4.2）。

4. 为什么重启后归零

本节是病根诊断，描述的是改动前的行为。下面四条已经全部在 M1 修掉， 改法与验收见改进方向 §9； 留着是因为「为什么会这样」比「改成了什么」更难重建，后面每个决定都从这里长出来。

4.1 普通会话在盘上不留痕迹（根因）

pipe-pane（把 pane 输出写进 logs/<id>.log）只在三处设置： swarm/members.go、spawn/spawn.go、plugin/hostapi.go。 ttmux new 与 Web「新建会话」走 runtime.CreateSession， 既不写 sessmeta 行、也不开 pipe-pane。 

$ find ~/.roam -newermt "2026-08-12 00:00" ! -newermt "2026-08-12 17:36" -type f
/home/ai/.roam/browser-config.json        # 17:36 重启前，当天唯一动过的文件

$ ls -lt ~/.roam/logs | head -2
2026-0811-1629-0009.log   Aug 11 16:29   # 最新日志是前一天的

那天下午有 15 个 Claude 会话在跑。Roam 主目录里连「它们存在过」都无从证明。 下面三条讲的是有记录的那一小撮如何被删掉；绝大多数会话根本没被记过。

4.2 sessions 表拿 tmux 的 $N 当主键

主键是 #{session_id}（$0/$3）。tmux server 随机器一起死， $N 全部消失，Reconcile 把「不在活会话里」的行硬 DELETE。 

$ sqlite3 ~/.roam/meta.db "select count(*) from sessions;"
0
$ tmux list-sessions -F "#{session_name}\t#{session_id}"
2026-0812-1740-0000  $0        # 重启后新建的会话，又拿到了 $0
2026-0812-1740-0002  $2

4.3 发现型项目按「此刻有没有会话」退场

// backend/api/project.go
if e.Origin != "user" && roamWts == 0 && p.Sessions == 0 && !e.Pinned {
    a.Projects.Remove(key)     // 重启后会话恒为 0 → 发现型项目在第一次刷新时全灭
}

判据的前提是「会话数是项目还活着的证据」。重启把这个前提废了。 实测台账里 发现型项目 = 0 个，只剩用户显式创建（origin=user）的那些侥幸存活。

4.4 $N 跨重启复用 → 静默串档

session-homes.json 以 tmux 的 #{session_id} 为键 —— 它渲染出来就是 $0 / $3，和本文说的 $N 是同一个东西， 不是两种键（这点容易看岔，代码注释里写作 #{session_id}（$3））。 它相对会话名确实稳定（改名不变），但相对 tmux server 不稳定：重起后从 $0 重新发号。

于是重启后建的第一个会话会继承上一代某个会话的归属目录，静悄悄归错项目。 reconcile(alive) 恰恰清不掉这种残行 —— 重启后 $0 又活了 （发给了新会话），它在 alive 集合里，残行被当成有效的保留下来。 这条比丢数据更难查：它给出的是错误的答案。

M1 已修：pin() 现在拿名字快照当换代探针 —— 同一个 $N 上 换了会话名，就判定是 server 换代后的复用，按新会话自己的 cwd 重钉而不是继承 （会话名是持久 id，活着的时候不会变，所以「名字变了」只可能是换了会话）。

5. 项目 ↔ 会话：一条没有外键的跨层 join

这是两层分裂最贵的地方。项目在 Roam 层、会话在 ttmux 层，它们之间没有任何外键， 关联是每轮现算出来的一条长链： 

tmux pane cwd  （运行时，会漂）
   ↓ 首次见到即钉死
session-homes.json: $N → home_dir       （Roam 层，键是易失的 $N —— §4.4 串档就出在这）
   ↓ ResolveRepo（git 主仓库根）
projects.json: dir → 项目 id                （Roam 层）
   ↓ 非 git 项目再按「最长前缀命中」兜底认领
项目卡上的「N 个任务」

链条上任何一环断了，项目卡就空 —— 而且看不出是断在哪一环。 重启后你看到的「项目卡全空」，实际断点在第一环（tmux 没了）和第二环（$N 失效）。

这正是改进方向里 M2 并库要解决的。sessions.project_id 一列外键，把这条现算的长链 换成一次 JOIN：会话死了行还在、项目还认得它，卡片上就能直接显示 「3 个已结束的任务，最近一次在 .worktrees/task」。 现在这条链只能回答「此刻」，答不了「有过什么」。
