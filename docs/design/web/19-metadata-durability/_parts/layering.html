3. 分层原则：台账 / 配置 / 大对象

病根之一是「所有持久化都被当成同一件事」，于是台账用了改一个字段就全量重写的 JSON， 而会话历史被交给 tmux 保管。三类数据的要求完全不同，存法也该不同：

类别特征存法例子
台账有关系、要事务、要按条件查、会长期累积SQLite meta.db，带 schema 版本与迁移项目、会话、归属、父子、竞赛、蜂群
配置单写者、无关系、人手要能改、量小JSON 文件，保持现状偏好、浏览器/手机/语音配置、导航站、TOTP
大对象只追加、体量大（本机 38MB 日志）、按 id 直取文件系统，DB 里只存索引logs/<id>.log、对话 transcript

另有一条正交的划分——什么是真相源，什么是现算的：

  • 台账（持久）：项目、会话、归属、父子、竞赛、蜂群 —— 存 meta.db。
  • 运行时（一次 tmux server 生命）：谁 attach、activity、pane 尺寸、$N —— 只问 tmux，不入库。
  • 派生（一次请求）：git 状态、worktree 列表、pane 内容、waiting 判定 —— 现算，入库只会不一致。
现在的错误在于把台账的一部分（会话是否存在过）交给了运行时层保管。 tmux 只该回答「现在谁活着」，不该回答「有过什么」。
