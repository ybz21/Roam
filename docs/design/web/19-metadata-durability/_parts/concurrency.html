9. 并发、写入口与迁移

9.1 一套库，不分层——但要分「谁写哪张表」

ttmux 层和 Roam 层不再各存各的，物理上就是一个 meta.db、一套 schema、一套迁移。 「两层」在改完之后只是代码归属，不再是存储边界 —— 问题篇里那张「一个目录两套机制」的图， 到这里就作废了。

但有一件事不能跟着一起取消：每张表只有一个写者。两个进程写同一个 SQLite， WAL 能让读写并发，写本身仍然是串行的；真正省掉锁竞争的不是 WAL，是「不会有两个进程同时想改同一批行」。 这不是把层分回来，是按数据的归属分：

表写者另一边怎么办为什么
sessions · tmux_epochsttmux CLI后端只读；要写就调 ttmux 子命令会话 id 的唯一出处在 CLI，编排逻辑也在 CLI（「薄封装」原则）
swarms · swarm_membersttmux CLI同上蜂群编排整个在 CLI
plugin_sessions · plugin_findingsttmux CLI同上插件宿主在 CLI
projects · project_aliases · project_tracesRoam 后端CLI 不碰项目是 Web 侧的概念，CLI 里没有
racesRoam 后端CLI 不碰竞赛只有 Web 有入口
唯一的跨写者动作是「建会话时顺手 touch 项目」。它现在也不是一个事务 —— CLI 建会话、后端下一轮轮询时才把项目记上。并库之后可以合成一个事务， 但那要求 CLI 也能写 projects，就破了上面的单写者。 建议维持现状：项目台账本来就是「读时收敛的读模型」，晚一轮记上没有任何影响， 不值得为它引入双写。

9.2 后端要不要直连这个库

一个容易被忽略的实情：后端现在连 sqlite 依赖都没有（backend/go.mod 里没有 modernc.org/sqlite），它对 meta.db 完全不知情，所有访问都是 exec 一次 ttmux ... --json。所以「一套库」落地时有个明确的岔路：

方案代价收益
全走 CLI（不加依赖）项目页要会话历史 → 每个项目 exec 一次，退化成 N 次进程启动架构最一致，后端零 DB 知识
只读直连 + 写走 CLI后端多一个 sqlite 依赖，且必须守住上表的写者约定问题篇 §5 那条跨层长链换成一次 JOIN
选后者。并库的全部意义就在于「项目卡上能直接显示会话历史」—— 如果读还是一次一次 exec，那张表并不并在一起没有区别。 写仍然走 CLI，所以「薄封装」原则一点没破：后端不重实现任何编排逻辑，它只是换了一种更便宜的读法。

9.3 一个该留在外面的例外：蜂群 posts

「一套库」有一处值得破例。每个蜂群现在有自己的 swarms/<群>/swarm.db， 里面是 members / cards / posts：

  • members / cards 并进主库 —— 它们要和 sessions join （成员会话死了还得找回它的日志），正是并库要解决的问题；
  • posts 留在每群自己的库 —— 它是广场聊天流，是全系统写得最频繁的表， 并进主库只会让主库的写锁竞争明显变差；而且「删掉一个蜂群」现在是删一个目录， 并进去之后要变成一串带外键的 DELETE。
判据不是「它属于哪一层」，而是写入频率和生命周期： 需要跨实体 join 的进主库，只在自己生命周期内高频追加的留在旁边。 这和 §2 把日志、transcript 留在文件系统是同一条原则。

9.4 连接层

  • PRAGMA journal_mode=WAL、busy_timeout=5000、foreign_keys=ON；
  • 进程内单例 *sql.DB；单写者内部的多表写走一个事务（建会话 = 写 sessions + 记 tmux_epochs）；
  • 统一放进新包 internal/metadb，sessmeta / swarm / plugin 都改用它； 后端用同一个包的只读入口。
CLI 必须能独立工作。库的位置、建库、迁移全部由 CLI 负责 —— 后端没起、甚至没装， ttmux 也要照常能用。所以「一套库」的落点是 <dataDir>/meta.db（CLI 的地盘）， 后端是接进来的那一方，不是反过来。
