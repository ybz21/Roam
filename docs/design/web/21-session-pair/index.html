会话结对 — 把一个会话拖进另一个会话

把左边任务列表里的一个会话拖到右边正在用的会话上——落下之后， 往当前会话里注一段话，告诉它旁边那个是谁、怎么跟它说话。 就这些。没有链路对象、没有配额、没有转发器、没有新命令： 发消息的能力 ttmux send 早就在了，剩下的交给大模型自己安排。

01能力已经在了，缺的只是「它不知道」

// cli/ttmux-cli-go/internal/command/session/commands.go:368
ttmux send <会话> <消息>
   ├─ rt.Resolve(会话)                会话名 / tmux id / 展示名 都认
   └─ rt.SendPromptSubmit("=名:", 消息)
         paste-buffer 落文本 + 独立回车——对方 pane 里出现这行并提交，
         和人亲手敲进去没有区别

所以「两个 Agent 怎么通信」这一问，答案是今天就能通信， 一行命令的事。真正缺的是两样：

1
Agent 不知道有这条命令 它不会用它不知道的东西。ttmux send 在帮助里，但没人会去翻。
2
Agent 不知道对面是谁 会话名是 2026-0824-1501-006h 这种，Agent 手上没有这张表。

拖拽解决的就是这两件事：用一个手势，把「对面是谁 + 怎么发」当场告诉它。

为什么不做更多

上一版这份稿子设计了链路表、轮次预算、速率闸、往来记录、tell／unpair 四条新命令。全部砍掉——那是拿一套机器去替大模型做决定： 该说几句、该不该回、什么时候停，它自己判断得比我的计数器好。 真出了问题（比如两个 Agent 一直客套），人看着终端一眼就发现，Ctrl-C 就停了， 不需要我提前替他建一套闸门。

02注进去的那段话

这是本稿唯一真正的设计物，所以逐字推敲。它经 SendPromptSubmit 投进当前会话——也就是你正看着的那个 pane， 和你自己敲一段话进去没有区别： 

[Roam] 你旁边还有一个会话，可以直接跟它说话。

  它是谁：XiaoHui · fix-missing-search（codex）
  工作目录：/home/ai/codes/ybz/xh/XiaoHui
  会话名：2026-0824-1501-006h

  给它发消息：
    ttmux send 2026-0824-1501-006h "你的话"

  想让它回你，就在消息里带上你自己的会话名：
    ttmux send 2026-0823-1043-0001 "回复内容"

  它收到的是一行文字并自动回车，和人敲进去的没区别。
  第一句最好先说清你是谁、想让它干什么；也别一直客套着来回。
这一段里的每一样为什么非有不可
展示名 + 项目 + Agent 种类人读的那半。Agent 也靠它判断「这活该不该找它」
工作目录决定了能不能让它去看某个文件。缺了这行，第一句话多半要花在问路上
会话名（id）而不是展示名Resolve 认展示名，但展示名可以重复（同名取排序第一个）。 命令里用 id 才不会发错人
自己的会话名否则对面收到消息没有回信地址，只能干瞪眼
「和人敲进去没区别」这是这条通道唯一反直觉的性质：不是发到收件箱，是直接替对方按下回车。 知道了它才会斟酌第一句怎么写
「别一直客套着来回」两个 Agent 互相回「收到，我看看」能一直聊下去。一句提醒，不是一套闸门

文案走 i18n（pair.intro.*），中英双份；命令本身不翻译。

03落点

终端画面和会话标签都接。「拖到当前会话里」本来就是人的直觉， 而画面那块地看着像被文件拖放占着了——其实不是：路径拖拽用的是 application/x-ttmux-path，跟会话拖拽的 application/x-tt-session 天然分得开，两条路互不干扰。第一版只让标签接，结果就是往画面里拖没反应 （用户第一句话就是「怎么拖动不了」）。

04落下之后

不弹确认框。这一步只是往你自己的会话里发了一段话—— 和你在输入框里敲一句话按回车是同一件事，而那件事我们从来不问「确定吗」。 你看着它出现在 pane 里，不满意就 Ctrl-C。

也不做芯片、不做记录、不做状态条那一格。 往来就在两个 pane 里明摆着，那本来就是终端最擅长的事； 再画一份记录只是把同一件事说两遍，还得维护它和真实 pane 不一致的那些时刻。

要拦的两种情况（第二种是真机上撞出来的）

① 目标里没有 Agent 在跑。这条比想象的严重。投递是「粘一段文本 + 按回车」： 落进 Agent 的输入框，整段是一条消息；落进普通 shell， 每一行都被当成命令执行——包括介绍词里那两行示例命令。 第一次真机测试就撞上了：靶子是个空 shell，于是它真的替我发了一条消息出去 （✔ 已发送到 ds4-flash-docs …）。所以没有 Agent 在跑的会话不给落点。

② 不在同一台机器。ttmux send 走的是本机 tmux， 两个会话在不同机器上时它找不到对方，而 Agent 会拿到一句「会话不存在」然后开始瞎猜。

两种都拒绝并说清原因——明确拒绝好过让它撞一堵看不见的墙。

实现上有个坑：dragover 里把 dropEffect 设成 'none' 的话，浏览器干脆不投递 drop 事件——于是「不接」变成了静默失败， 人连原因都看不到。要一律 'copy' 接住，再在 drop 里解释； 高亮只给接得住的目标。（合成事件测不出这条：它绕过了浏览器那层判定， 真·鼠标拖一次才现形。）

验收时的一个观察：它不一定马上说话

真机上把介绍投给一个闲着的 Claude 会话，它读完之后没有去打招呼， 而是接着干自己手上的事。这是对的——介绍是上下文，不是指令。 硬让它发一句「你好」只会浪费两边各一轮。它有话要说的时候自然会用。

后端大概率一行不用改：投递就是 ttmux send， Web 侧本来就有往会话发东西的路径（发消息、开工都走它）。落地前先确认这条， 能复用就别新开路由。

不做什么

  • 不建链路对象。没有 pair 表、没有 unpair。 拖一下就是发一段话，发完这件事就结束了——状态留在两个 Agent 的上下文里， 那才是它该在的地方。
  • 不做轮次预算 / 速率闸 / hop 深度。该说几句、该不该回、什么时候停， 大模型判断得比计数器好。
  • 不做往来记录面板。往来就在 pane 里。
  • 不加新 CLI 命令。ttmux send 够了。
  • 不弹确认框。见 §04。
  • 不做跨机，也不往非 Agent 会话投。都不给落点，见 §04。

06验收

  • 拖任务卡到画面和到标签都要通；拖文件进终端仍然是插入 @路径（两条路没打架）。
  • 用真·鼠标拖一次，不是只发合成事件——合成事件绕过浏览器对 dropEffect 的判定，测不出「不接的目标静默失败」那类问题。
  • 落下后当前 pane 里出现那段介绍，并且真的自动回车了—— 裸 send-keys text C-m 只打字不发送，这条必须真机看。
  • 照着注进去的命令原样发一条，对面 pane 里出现并提交。
  • 对面按介绍里的地址回一条，回到发起方 pane 里。一个来回真的通， 这是这个功能的全部。
  • 展示名重复的两个会话：确认命令里用的是 id，发到了正确的那一个。
  • 跨机拖拽、以及目标里没跑 Agent：都不给落点，并说清原因。
  • 落点高亮：dragover 时标签亮成实心强调边，且不该接的目标不亮。

一句话

通信方法就是 ttmux send <会话> <消息>，它今天就能用。 这个功能要做的只是在对的时刻把这句话连同对面的地址一起告诉 Agent—— 剩下的它自己会。
