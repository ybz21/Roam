概览 × 项目 —— 合并成一个工作台

现在导航第一组里并排放着「概览」和「项目」两页。它们不是「总览 + 详情」的关系—— 概览的主体（活跃项目作战卡）和项目页的主体（项目卡栅格）画的是同一批卡片、拉的是同一条接口， 只是排序和筛选不同。真正只属于概览的东西只有三样：一行问候、一条「需要你」行动队列、一条最近活动轨； 而这三样都可以直接挂在项目页的顶上。

本稿的结论是把概览并进项目页：`#/projects` 成为唯一的工作台首页，`#/overview` 重定向过去， 导航从 8 项减到 7 项。合并顺带解决一个存量问题——概览为了画绿点/黄点， 每 6 秒对最多 14 个会话各发 3 条请求，重算的是后端 `/projects` 已经算好并返回过的字段。

重叠不止在版面上，还在数据链路上

两页拉的是同一条 GET /projects。这条接口的返回里，每个项目的 top[] 已经带了 running / waiting / branch / linked —— 后端一次 tmux list-panes -a 加一趟进程树扫描就全算出来了，只对在跑的会话补一次 capture-pane。

概览把这套判定又在前端做了一遍：它自己拉 /sessions?tree=1 拼项目归属，然后对最多 14 个会话 逐个打 /claude、/codex、/capture，6 秒一轮。 

// backend/api/claude.go —— 后端这个函数的注释里就写着这件事
// runningAgentSessions 一次性扫全部 pane 的进程树，返回跑着 claude / codex 的会话集合。
// 供项目列表批量判「活跃」——绿点语义（设计 W2）：避免前端逐会话打 /claude+/codex（N×2 请求）

// 而 Overview.tsx 现在是（每 6s）：
names.slice(0, 14).forEach(async (n) => {
  await api('GET', `/sessions/${n}/claude`)    // 后端 top[].running 已经有
  await api('GET', `/sessions/${n}/codex`)     // 后端 top[].running 已经有
  await api('GET', `/sessions/${n}/capture?lines=50`) // 后端 top[].waiting 已经有
})
// 峰值 42 条请求 / 6 秒，重算的是同一页另一条接口已经返回过的字段
为什么概览当初非自己算不可：后端 top[] 被截到 2 条（if len(top) > 2）， 而概览的卡片要显示 3 条会话行，还要区分 Claude / Codex 品牌标——top[].running 只是个 bool。 所以这不是「前端偷懒」，是接口差两个字段。合并后补上这两处，前端那套轮询整段删掉（见 §9）。

2 · 各自真正独有的东西

合并的前提是一样都不能丢。剥掉重叠部分之后，两页剩下的是：

只有概览有合并后上移到页头与右轨
  • 问候 + 一句话状态：「今天有 3 件事需要你」/「当前没有待处理事项」。这是首屏唯一回答「下一步做什么」的句子。
  • 状态条：运行中 / 等待输入 / 待收尾 / 蜂群，四个数都是导航入口，零值不渲染。
  • 「需要你」行动队列：最多 3 张卡，跨项目。这是概览的真正价值——它按「人不动就卡住」排序，不按项目组织。
  • 最近活动轨：跨项目的 commit + 合并留痕时间轴。
只有项目页有合并后原样保留
  • 搜索 / 筛选 / 排序（sticky 工具条）。
  • 置顶、删除、新建项目——项目作为存储对象的增删改。
  • 安静分组：无会话无待收尾的项目折成一行，不占整张卡。
  • 全量散会话，行尾带动作钮。
  • P2 详情深链 #/projects/<key>：composer、任务流、Worktree、编队、活动。整个 IA 的骨架。

6 · 排序、筛选与行动条的关系

两页的排序差异是合并里唯一需要新做决策的地方。概览按「需要你」排，项目页按「名称」排（默认）。 合并后把「需要你」加成排序下拉的第一档并设为默认，旧的三档原样保留：

排序档规则来自
需要你（默认）置顶恒最前；其余按「等待输入 + 待收尾 + 蜂群待解锁」条数降序，同数按最近活跃降序概览 projNeeds()
名称localeCompare，稳定项目页（原默认）
创建时间firstSeen 新在前项目页
最近活跃lastActivity 新在前项目页

筛选 chips 同理加一档「需要你」并置于最左，其余三档不变。选择仍持久化到 localStorage （沿用 SORT_KEY），所以习惯按名称找项目的人改一次就够了。

两条实现时才暴露的死角，稿子原来没写：
① 一打字就跳回「全部」。默认筛选是「需要你」，而搜索是「找这一个项目」的明确动作—— 两者叠加的话，搜任何没欠事的项目都只会得到「没有匹配的项目」。第一个字符落下就把筛选切到「全部」， chip 上看得见，不是隐形规则。
② 「需要你」为 0 时自动退回「活跃」。默认档在事项清零的那一刻会把整页变成空列表—— 空列表不是答案，是死路。

8 · 栅格阈值

两页现在的栅格规则不一样，而且合并后右轨会吃掉 320px，阈值必须重定。 阈值一律看 Canvas 容器查询，不看 viewport——终端坞开合只改 Canvas 宽度，不该由窗口宽度决定列数。

Canvas 宽行动卡项目栅格最近活动说明
< 9001 列1 列落到页尾手机 / 终端坞占了大半宽度的桌面
≥ 9002 列2 列落到页尾状态条并进页头右端，省掉一整行
≥ 11803 列自动右侧 320 sticky右轨挂出来，栅格可用宽随之少 320
落地时项目栅格没有写断点。行动卡是固定三档（它一行最多三张，是刻意的封顶）， 但项目卡用的是 repeat(auto-fill, minmax(320px, 1fr))——列数由**栅格自己剩多少宽**决定， 右轨挂不挂出来它都对，不需要为「1180 挂轨、1560 才够三列」各写一条规则。 原概览写死的「≥1320 → 3 列」恰恰是这里出错的地方：它同时在 ≥1180 就挂了右轨， 1320 减去 320 只剩 ~980，三列每列 320 会挤破下限。auto-fill 不会犯这个错。

容器宽度上限：概览用 --content-overview: 1680px，项目页用 .prj-wrap-wide { max-width: 1180px }。 合并后取 1680——项目页那个 1180 是在没有右轨时定的，带上右轨就只剩一列半。
