连续工具调用的篇幅压缩 — 运行组

真机上连着跑五条 Bash，一屏就没了——每条都是一张独立描边卡：上下 8px 外边距、 1px 描边、终端底色、一行命令、再加一行 description。信息量是「跑了 5 条命令、68 行输出」， 篇幅却是 430px。这一稿把连续的同族工具收成运行组（ToolRun）： 一组共用一条左脊、一个组头；跑完且全成功的组自动折成一行； 失败与被拒的行永远留在外面。目标是「历史像索引、当下像现场」。

这一稿只改「排版密度与分组」，不改任何解析。 工具怎么认、diff 怎么算、错误怎么判，全部沿用 设计 15 已落地的那套； 这里新增的是消息列表层的一次分组，和 CommandRow / ToolCard 的一套「行模式」。

2 · 设计总纲：四条规则

规则说明解决的问题
① 成组相邻的工具调用（跨消息，中间没有正文）并成一个运行组：共用一条左脊、一个组头，行与行之间没有外边距、没有描边。五张卡的边框与间距 → 一个外壳
② 跑完就收组内全部有结果、且全部成功时，自动折成一行摘要：终端 · 5 条 · 68 行。正在跑的组保持展开。历史区从 430px → 44px
③ 失败不折失败 / 被拒的行提到组头下面单独列出，不参与折叠，红条永远第一眼可见。「跑完就收」不能把报错也收走
④ 行只留信息去掉每行的描边与终端底；description 并到同一行行尾（灰字，窄屏不显示）；量感（68 行 / +64 −9）收进右侧定宽槽，一列对齐。单行 86px → 44/26px
为什么分组必须发生在「消息列表层」而不是消息内。 截图里那五条命令是五条独立的助手消息（Claude 每次工具调用单独成条）。 Message.tsx 里现有的 segments() 只在一条消息内部把工具块并段—— 对这个场景一点用都没有。分组要在 ChatShell 渲染消息数组时做： 连续的「纯工具消息」（没有 text/thinking 块）合并成一个 run。
终端组 Bash / shell / exec_command 改文件组 Edit / Write / apply_patch 读查组 Read / Grep / Glob / WebFetch 失败行 任何组里出错的那条

4 · 连续改同一个文件：合并成一张 diff

「改文件组」比终端组还费篇幅：现在每次 Edit 都是一张卡 + 一张 diff 面板， 连改同一个文件三处就是三张。合并规则：同一个运行组内、同一路径的连续 Edit/Write， 并成一张 diff 卡，标题写 ×3，展开后三处变动顺序拼接，段间一条细分隔线标「第 N 处」。 统计合并成一份 +64 −9——这也正是人下一句要问的「这个文件到底改了多少」。

6 · 折叠时机：一台很小的状态机

「自动折叠」最容易做坏的地方是跟用户抢方向盘：人刚展开看输出，一次轮询回来又给收了。 规则写死成三条，任何时候都不许违反。

run.state =
  live     ← 组里还有 tool_use 没配到 result
  settled  ← 全部有结果

渲染时的 open：
  userToggled.has(run.key)  → 用用户那次的值，永远优先
  state === live            → 展开（跟着现场走）
  state === settled && 全成功 → 收起
  state === settled && 有失败 → 收起，但失败行提到组头下面，单独展开

run.key = 组内第一条 tool_use 的 id      // 不用下标：轮询插入新消息会整体位移
userToggled: Map<string, boolean>       // 存在 ChatShell，随会话切换清空
  • 用户开过的组，此后永不自动收。哪怕组从 live 变成 settled，也只按用户那次的值走。
  • live → settled 的那一刻会「塌」一下：正在看的组突然收起是很讨厌的。 所以只在该组不在视口内时立刻收；在视口内则等到有新消息追加到它下面再收， 塌陷发生在视线之外。
  • 状态条的「跳到错误」要能穿透折叠：StatusBar 现在按 data-msg-id 滚过去，如果那条被折进组里就滚了个寂寞——跳转前先把目标所在的组置为展开 （写进 userToggled），再 scrollIntoView。
  • 浏览器 Ctrl+F 搜不到被折起的内容，这是折叠的固有代价。缓解：组头摘要里带最后一条命令原文； 真要全文找走会话搜索（⌘K），那本来就是搜转录全文的。不做「搜索时自动展开全部」—— 那等于随机把 430px 还回来。

9 · 一套结构，两端适配

手机与桌面不是两套设计，是同一份 DOM 在两种密度下的两种落法： 组头、行、输出三层结构完全一致，组件也只有一套（ToolRun + RunRow）。 差异全部靠 <html> 上的 data-size / data-pointer 走 CSS， 组件里一个分支都不写（设计系统硬规则：断点只有 useLayout() 一个入口， 纯样式差异不进 JS）。

维度手机 data-size="compact"桌面 regular / large怎么实现
结构完全相同：左脊 → 组头 → 行 → 输出同一份 JSX
可点行高44px（data-pointer="coarse"）26px@media (pointer:coarse)
纯展示行高26px —— 不是按钮就不受 44 约束不加 .is-clickable
行尾 description隐藏（挤掉命令本身不值）显示，最宽 34%[data-size=compact] .cc-run-desc{display:none}
组头「最后一条」显示，但让位给量感槽显示全宽同一条 flex:1 1 auto + min-width:0，自动让位
量感槽宽度自适应，只留一项（68 行 或 +64）定宽 52px，+N −M 两列对齐桌面加 width:52px，手机 width:auto
展开输出手风琴：同组同时只开一条不限制useLayout().size 传一个 accordion 布尔
输出最大高190px320px（沿用现有 .cc-cmd-out）CSS 变量 --run-out-max
复制按钮常驻 opacity:.55hover 出现现有 .cc-toolcopy 规则，不改
折叠规则完全相同（§6 那台状态机，与视口无关）纯逻辑
唯一进 JS 的那一处是手风琴，因为它是行为不是样式。走 const { size } = useLayout() 拿一个 accordion = size === 'compact' 布尔传进 ToolRun——不读 window.innerWidth，不自己 matchMedia。 其余全是 CSS，改断点时不用碰组件。

10 · 交互与可达性

项规则
命中区粗指针下可点的行（组头、可展开的命令行）自身 min-height:44px； 纯展示行（成功的 Read、没有输出的命令）不是按钮，不受 44 约束，保持 26px。 不用伪元素撑命中区——设计 15 试过，44px 伪元素在 1px 间距的行之间会溢出 ±10px， 后面的兄弟节点盖在上面，点谁都不准。
手风琴手机（data-size="compact"）下同一组内同时只展开一条输出： 展开第二条时自动收起第一条。桌面不限制。理由：手机上展开三段输出等于把刚省下的 430px 又还回去。
键盘组头与行都是 role="button" tabIndex=0， Enter/Space 切换；aria-expanded 如实给。 组头的 aria-label 要念得出内容：「终端组，5 条命令，68 行输出，已折叠」。
复制复制按钮跟到行上（hover 出现 / 粗指针常驻 .55 透明度）。 组头也给一颗：复制整组命令，一行一条——这是「把刚才那串命令抄下来」最常见的用法。
动效折叠只做 height 过渡 120ms， prefers-reduced-motion 下直接切。不做逐行淡入，长列表上会掉帧。

12 · 不做

  • 不做「全部展开 / 全部收起」总开关。看起来很省事，实际上人只想看某一处； 给了总开关就会有人一键全开，然后回到 430px。
  • 不把正文也折进组里。组只装工具。助手说的话永远平铺——那是这一页真正的主体。
  • 不做跨用户回合的分组。一次用户提问到下次提问之间才可能成组； 跨回合合并会让「这一步是回应哪句话」彻底丢失。
  • 不改任何解析、判定与 diff 算法，全部沿用设计 15 已落地的实现。
  • 不做虚拟滚动。密度做完之后，一屏的 DOM 量已经降一个量级；虚拟滚动会跟 「跳到错误」「保持底部」两处现有逻辑打架，收益不抵成本。
