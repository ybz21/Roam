Claude / Codex 对话渲染精细化

对话页现在「能看」但不精细：每个工具调用都是一张同样的描边卡，连着十几次 Read 就把正文淹了；Edit 的 diff 是假的（旧的整块打 -、新的整块打 +）； 成功和失败一个待遇，真正该被看见的报错反而不显眼；Codex 侧还另写了一份近乎重复的渲染。 这一稿把它改成：该占一行的只占一行，该展开的才展开，失败永远最显眼，Claude 与 Codex 共用一套。

架构与 LCS 差异算法参考 CloudCLI UI（https://github.com/siteboon/claudecodeui， 同为 AGPL-3.0）。它的组件是 Tailwind + 写死色阶类名，跟本仓库「只用令牌、全站蓝绿各一支」冲突， 所以只借架构和算法，皮按本仓库令牌重写；署名按其 AGPL 第 7 条附加条款补进 README / NOTICE。

10. 分层：per-provider 的代码只许存在一层

第 6 节那张对照表如果直接写成「前端一张大表里混着两套工具名」，能跑，但每加一个 agent 那张表就膨胀一次， 而且 provider 的差异会渗进渲染层 —— o.file_path ?? o.path ?? o.notebook_path 这种缝合就是渗漏的痕迹。 切成四层，把认得 provider 的代码收敛到唯一一层。 

L0  转录解析（Go，已有）
    backend/api/claude.go · codex.go —— 只认「文件在哪、JSONL 什么格式」
      ↓ cBlock 流  {kind, text, name, input, id, toolUseId, isError}
        「一条消息由若干块组成」的通用模型，provider 中立，不用动

L1  拉取与配对（chat/useTranscript.ts，已有）
    增量 offset、tool_result 挂回 tool_use —— 认块流，不认工具
      ↓ Msg[] + results

L2  适配层（新增 chat/adapters/*.ts）          ★ 唯一 per-provider 的一层
    provider 的工具词汇、入参形状、成败判定 → 语义调用
      ↓ ToolCall + ToolOutcome

L3  呈现（chat/tool-view.tsx + tool-parts.tsx）
    只认语义，永远不知道 Claude / Codex 存在

关键是 L2 与 L3 之间那条线：跨过去之后就没有 provider 了。

语义工具是闭集

这是整个设计能成立的前提 —— 工具的种类有限，工具的名字无限。kind 决定档位，加新工具改这里，加新 agent 不改这里。

export type ToolCall =
  | { kind: 'shell';   command: string; description?: string; cwd?: string }
  | { kind: 'read';    path: string; line?: number }
  | { kind: 'edit';    path: string; before: string; after: string; mode: 'edit' | 'create' }
  | { kind: 'patch';   files: PatchFile[] }
  | { kind: 'search';  query: string; scope?: string }
  | { kind: 'plan';    items: TodoItem[]; note?: string }
  | { kind: 'agent';   title: string; role?: string; prompt: string }
  | { kind: 'ask';     questions: Question[]; answers?: Record<string, string> }
  | { kind: 'fetch';   target: string }
  | { kind: 'mcp';     server: string; tool: string; args: string }
  | { kind: 'unknown'; name: string; args: string }     // 兜底，永远不空

export type ToolOutcome = {
  status: 'running' | 'ok' | 'error' | 'denied'
  text: string
  files?: string[]        // Grep/Glob 抽出的命中列表
  exitCode?: number       // Codex 有，Claude 没有
}

一个 provider＝一个文件

export interface Adapter {
  id: string
  accent: string                            // 蓝 / 绿
  thinkingLabel: () => string               // 「思考过程」/「推理」
  transcriptPath: string                    // 'transcript' | 'codex-transcript'

  toolCall(block: Block): ToolCall                     // 纯函数，可快照测试
  outcome(call: ToolCall, result?: Block): ToolOutcome // 成败判定属于这里
  cleanUserText(text: string): UserText
  status(raw: RawStatus): AgentStatus                  // 见第 11 节
}

于是两个容器塌成配置，AgentChat 里不存在任何 if (side === 'codex')： 

export default function ClaudeChat(p: Props) { return <AgentChat {...p} adapter={claudeAdapter} /> }
export default function CodexChat (p: Props) { return <AgentChat {...p} adapter={codexAdapter} /> }

三条边界，为什么这么切

  • 语义映射放前端、不推到 Go。Go 要重新 build + 重装才生效，前端 build 完拷进 dist 刷新就见效； 工具渲染是纯呈现关切，Web 是唯一消费者。块流解析必须在 Go（文件定位、增量 offset）， 工具语义必须在前端（跟档位、图标、折叠策略强耦合）—— 这条线不该挪。
  • 不改后端 IR。cBlock 看着像偏向 Claude，但它其实是通用的块模型，Codex 已被成功翻译进去。 真正有损的只有一处：Codex 的退出码被 is_error 布尔压扁了。 给 cBlock 补一个 meta map[string]string 让适配层拿到原始信息，比重做 IR 划算得多。
  • 这不是为「将来可能加第三个」买单。支撑它的是三条现在就成立的理由： ① 入参形状差异已经长出缝合代码；② 成败判定必须 per-provider，缠在 JSX 里没法测； ③ adapter 是纯函数，可以直接喂真实转录片段做快照测试 —— chat/ 下现在一个测试都没有，正是因为逻辑全缠在 JSX 里。

代价：多一层、约 200 行、tool-render.tsx 拆成 adapters/ + tool-view.tsx。 已写好的显示件 tool-parts.tsx 一行不用动 —— 它本来就不认识工具，只认识「一行 / 命令 / 卡片 / diff」。

切分层顺手落掉的两个坑

① Codex 的失败判定天生比 Claude 弱。Claude 的 tool_result 有 is_error 字段； Codex 协议里没有，后端只能从输出里抠退出码：(?i)(?:exit code|exited with code):?\s*(\d+)。 于是 git diff --exit-code、grep 没匹配这类正常的非零退出会被染成红色故障。 判定逻辑归 adapter 之后，Codex 侧可以单独降级：不染红，只在行尾标灰字 exit 1 —— 白名单永远列不全，而「退出码 1」本身已经是完整信息。Claude 侧一行不受影响。
② MCP 结果不带 call_id —— 现在会永远转圈。后端处理 Codex 的 mcp_tool_call_end 时， 一条消息里同时塞了 tool_use 和 tool_result，但两个都没有 id； 而 pairToolResults 只按 id 配对。结果是 MCP 调用永远显示「运行中」，结果被当成孤儿另画一遍。 补一条同消息内相邻位置配对的兜底，放 L1 —— 那是块流层面的事，不是工具语义。

12. 等你拍板：权限确认怎么呈现

选择框是整个对话页里唯一「活的」东西 —— 别的全是已经发生过的历史，只有它在等你按一下。 它的来源也不一样：不在转录里，是从终端实时画面（capture）解析出来的 （frontend/src/prompt.tsx 已经在做这件事），点一下经 POST /sessions/:name/keys 注入原始按键。这条性质差异决定了它的呈现规则。

两条时序上的坑

① 两条流不同步。选择框走 capture 轮询（1.2s），消息流走 transcript 轮询（1.5s）， 是两条独立的流。必然出现「已经答完了但工具行还挂着待确认」的中间态。 处理：选择框一消失就乐观清掉那条工具行的待确认态，等下一轮转录对账。反过来不成立 —— 不能等转录，那样黄条会多挂一秒多。
② 别把 Agent 输出的编号列表误判成选择框。detectPrompt 已经踩过这个坑， 现在的判据是「从 1 起的连续编号 + 至少两项 + （有游标 或 明确提问句 + Enter/Esc 操作提示）」。 新渲染让这个误判的代价变大了 —— 以前误判只是底部多一块面板， 现在还会把一条正常的工具行染成黄色「待确认」。所以那条工具行的黄色要额外要求「该工具确实没有结果」 才染，有结果的一律不染。
