决策：不再维护 redroid 容器这条路，Android 侧的「虚拟机」统一由 Android SDK 的 AVD 承担。本文是改造前的方案与迁移路径。

一 · 现状：那台 TV 模拟器不是 ttmux 起的

sdk_google_atv64_x86_64 是 adb 报的 ro.product.model，不是 AVD 名。它的真身是 AVD xh_tv1080p，由另一个项目（XiaoHui 电视端）的脚本拉起，与 ttmux 无关。

ttmux 这边 backend/phone/android.go 开篇就写着「MVP 不负责拉起模拟器/容器，只附着 + 操作」。 落盘配置 ~/.roam/phone-config.json 就是附着结果：{"mode":"device","address":"emulator-5554"} —— 一台模拟器被记成了「本机设备」。

而 redroid 那条路在这台机器上的真实处境
  • 没在跑：无 ttmux-redroid 容器；binder 未加载（模块在 /lib/modules/7.0.0-28-generic/…/binder_linux.ko.zst，每次起都要 sudo modprobe）。
  • 封顶 Android 15：内核 7.0 已移除 ashmem，脚本会自动把目标从 16 回退到 15。
  • 磁盘已经压了 7.3G：redroid/redroid 的 13 / 15 / 16 三个镜像都拉过（2.29 + 2.41 + 2.57 GB）。
  • 拿不出 TV 镜像：redroid 只有纯 AOSP 手机镜像，而当前要验的正是 Android TV。

二 · 决策：为什么是「换掉」而不是「并列」

两者不是同一类东西：redroid 是容器（Android 用户态直接跑在宿主内核上），AVD 是虚拟机（QEMU + KVM，自带 Android 内核）。 差别几乎全从这一点派生 —— 也正是这一点，让 redroid 的成本落在了「宿主内核」上，而这恰恰是我们最不该去要求用户改的地方。

维度本地 redroid（移除）AVD（保留并接管）
宿主依赖内核要有 binder（sudo modprobe）+ ashmem；本机无 ashmem → 封顶 A15只要 /dev/kvm（本机已有，属 kvm 组）
平台仅 LinuxLinux / macOS / Windows
系统镜像纯 AOSP 手机，无 GMS / 无 TV / 无 WearGoogle APIs、Play Store、Android TV、Wear、API 21–36、官方机型档
ARM 应用要专门的 arm-translation 镜像，且不稳自带 ARM 转译，arm64-only 的包照装
分辨率容器创建参数，改一次要重建容器wm size/density 随时改，AVD 配置里也能定死
传感器/相机/来电/GPS基本没有全套 extended controls + 控制台 API
快照无（容器 stop/start 秒级，/data 持久）snapshot / quick boot
内存 / 启动~1–2G，秒级本机实测 4.9G，冷启 30–60s（快照 ~10s）
密度一台服务器十几个三四个吃满 30G
维护方我们自己写的 165 行自适应脚本Google 官方工具链
我们放弃了什么
  • 实例密度：将来做「安卓池 / 蜂群一人一台」时，AVD 的 5G/台会先撞上内存墙。
  • 秒级起停：AVD 即便走快照也要十来秒。
  • 已拉的 7.3G 镜像与 ~/.roam/android/data 里的容器数据 —— 不自动删，见迁移一节。

这三条都不影响当下：本机内存 30G、真正要验的是 TV，而密度是个还没到来的需求。真到那天，它该以「远程安卓池」的形态回来，而不是塞回设置页的一档。

我们没有丢的东西
  • 网络 adb 这条传输照旧：原「远程 redroid」改名「远程设备」，仍是 adb connect host:port —— 无线调试的真机、别人机器上的模拟器、乃至别人自己起的 redroid，都还连得上。
  • 本机真机（USB）不动。
  • 换句话说：删掉的只是「由 ttmux 用 docker 拉起并管理一个 redroid 容器」这套生命周期，不是「连接一台远端安卓」的能力。

四 · 新建模拟器（不只是接管现有的）

只能用「已经存在的 AVD」是半个功能：新机器上一台都没有，用户还是得回命令行。所以设置页要能从零建出一台。 难点不在表单，在于它不是一个秒回的操作 —— 本机就是活证据：

$ sdkmanager --list_installed
system-images;android-36;android-tv;x86_64   # ← 全机唯一一个系统镜像（8.2G）

要建一台手机 AVD，第一步必然是下载一个 1.5–2.5G 的系统镜像。所以「新建」必须按下载任务来设计， 不能是个转圈的 Modal —— 这决定了它的实现形态，也决定了它排在接管功能之后。

4.2 接口与实现

新增backend/phone/android_avd_create.go与 android_avd.go（发现/起停）分开：一个管生命周期，一个管目录与创建
接口做什么
GET /phone/avd/catalog 机型档（avdmanager list device）+ 系统镜像目录（sdkmanager --list，分「已安装 / 可下载」并标包大小）。 远程 fetch 实测要好几秒 → 缓存 10 分钟，带 ?refresh=1 强制刷新。
POST /phone/avd 立即返回 taskId，后台跑：① 缺镜像则 sdkmanager <pkg> 下载 → ② avdmanager create avd -n … -k … -d … → ③ 改写 config.ini → ④ 可选立即启动。
GET /phone/avd/tasks/:id SSE 流式回日志与百分比。复用 backend/stream/stream.go 的 writeSSE()，不新造一套推送。 sdkmanager 的进度行形如 [==== ] 45% Downloading …，按 (\d+)% 抽百分比，原始行照样进日志区。
DELETE /phone/avd/:name avdmanager delete avd -n <名>。破坏性：二次确认，说明会连 ~/.android/avd/<名>.avd 里的应用数据一起删； 正在运行的先拒绝，要求先停。

config.ini 改写照搬 tv_emulator.sh 里那段 python 的语义（读成 kv、覆盖、写回），用 Go 实现： hw.ramSize / vm.heapSize / disk.dataPartition.size / hw.gpu.enabled|mode / hw.dPad / hw.keyboard / hw.lcd.width|height|density。 这一步不能省：avdmanager 建出来的 TV AVD 未必带 dPad，而没有方向键的电视等于砖头 —— XiaoHui 的脚本当初要多写那段 python，就是为这个。

六个必须处理的坑全部有本机实测依据
1许可未接受会卡死 sdkmanager 未接受许可时进入交互式 y/N 等待，后台任务就此挂住直到超时。必须先 --licenses 预接受； 且这一步要用户在 UI 上明确点「接受 Google Android SDK 许可」，不能替他默默 yes | 过去。
2cmdline-tools 可能落后 本机实测告警：This version only understands SDK XML versions up to 3 but an SDK XML file of version 4 was encountered （装的是 commandlinetools-linux-11076708）。目前仍能工作，但 catalog 接口要探测并提示升级。
3cmdline-tools 可能压根没有 只装 Android Studio 的人常常没有它。需要一条引导安装路径 —— 蓝本就是 tv_emulator.sh setup 里那段 curl commandlinetools-linux-*.zip 解压到 $SDK/cmdline-tools/latest。
4不要用 --force avdmanager create avd --force 会覆盖同名 AVD 连同其数据。必须先查重、报错让用户改名，绝不代他覆盖。
5磁盘 一个镜像 2–3G + data 分区 6G。创建前查可用空间，不足就拦下并说清缺多少（本机 / 余 474G，宽裕； 现有 ~/Android/Sdk/system-images 已占 8.2G）。
6任务不能绑在请求上 下载 2.3G 视网速要几分钟到几十分钟，远超任何 HTTP 超时，用户还会关抽屉、切页面、锁手机。 所以 POST 只发号，进度走 SSE，任务活在后端；抽屉关了任务继续，完成后设备列表自动多出一台。

新增backend/phone/android_avd.go按内容命名，不叫 helpers/utils
  • listAVDs() — emulator -list-avds。二进制定位：$ANDROID_SDK_ROOT → $ANDROID_HOME → ~/Android/Sdk/emulator/emulator → PATH。
  • avdNameOf(serial) — adb -s <serial> emu avd name，把运行中的 emulator-* 映射回 AVD 名。 整套方案的支点：没有它就分不清「这台 AVD 是不是已经在跑」，列表会同时冒出「运行中的 emulator-5554」和「未运行的 xh_tv1080p」两条幽灵。实测本机可用。
  • startAVD(name) — emulator -avd <name> -no-window -no-audio -no-boot-anim -accel on -gpu <探测>， detached（Setsid 脱离后端进程组）：ttmux 重启不能把用户的 VM 带走。日志落 ~/.roam/android/avd-<name>.log，随后轮询 sys.boot_completed。
  • stopAVD(serial) — adb -s <serial> emu kill。
  • GPU 探测规则从将被删除的 android-redroid.sh 搬进 Go（这是那个脚本里唯一值得留下的东西）： renderD 节点是 Intel(0x8086)/AMD(0x1002) → -gpu host，跳过 NVIDIA(0x10de)，都没有才 swiftshader_indirect。 本机 renderD128=Intel、renderD129=NVIDIA，规则命中前者 —— 比 XiaoHui 脚本写死的软件渲染快一截。
  • 启动串行化：沿用 installMu 的 TryLock 写法，重复点击快速返回「启动进行中」。

风险
  • 别把用户的 VM 带走：后端起的 emulator 必须 detached，ttmux 重启/退出不得连带 kill；反过来「停止」只作用于当前选中目标，UI 上要说清它会关掉整台机器。
  • 不是我们起的也能停：本机这台是 XiaoHui 脚本起的，接管后 ttmux 照样能 emu kill 它 —— 这是能力也是脚，按钮文案要写明白。
  • KVM 权限：Linux 上用户须在 kvm 组，否则 -accel on 直接失败；启动失败时把 /dev/kvm 的检查结论写进日志区，别只回一句「启动失败」。
  • 无 GUI 的服务器：必须 -no-window，这也是我们默认加的。
  • 删除模拟器是真删：avdmanager delete avd 连同 ~/.android/avd/<名>.avd 里的应用与数据一起没。 二次确认要写清删的是什么，且运行中的一律先拒绝 —— 不做「帮你先停再删」这种贴心。
  • 不代替用户同意许可：Google Android SDK 的许可必须由用户在 UI 上点过，后端才 --licenses。这一步不做「静默通过」。
  • 下线是单向的：redroid 的价值在「多实例安卓池」，真需要时应以远程服务的形态回来（走「远程设备」那档连过来即可），而不是把这一档再塞回设置页。
