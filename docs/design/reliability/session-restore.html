Roam · Reliability

R2 会话懒恢复

2026-08-23 早上开机，会话列表是空的——17 个连续跑了 11 天的会话一个不剩。 但它们并没有丢：台账全都记着。丢的不是数据，是那条通往数据的路。 这份稿子把恢复做成懒的：会话一直在列表里，开机时一个都不建， 你点哪个，哪个才真正活过来。

三版定调，最后落在这里

v0.1开机弹横幅问「要不要恢复」 否 — 把该自动的事变成用户的作业
v0.2开机自动把 17 个壳全建出来，agent 懒启动 仍然多余 — 你当天只会点开两三个，其余 14 个空 tmux 会话白建
v0.3什么都不建。列表从台账渲染，点击才恢复 本稿

01核心：会话的「在」与「活」是两件事

今天的会话列表只有一个数据源：tmux list-sessions。tmux 里没有 = 列表里没有 = 用户眼里「消失了」。懒恢复要做的第一件事，是把这两个概念拆开：

在（台账说了算）

这个会话属于哪个目录、叫什么名字、上次跑到哪、agent 对话 id 是多少。 这些从来没丢过，一直在 ~/.roam/meta.db 里。 机器重启带不走它们。

活（tmux 说了算）

有没有一个真实的 tmux 会话、pane 里有没有进程在跑。 这个确实被重启带走了，而且救不回来——救回来的只能是一个新的壳。

拆开之后，「重启后会话消失」就不再是一个恢复问题，而是一个列表渲染问题： 列表该显示「在」的全集，其中一部分正好也「活」着。没活的那些不是不存在， 只是还没被点开。

这样一来，恢复动作根本不需要一个时机

不需要开机自启去做什么，不需要主动 start-server，不需要批量恢复的限流， 不需要担心 ttmux-web 重启导致重复恢复，不需要「撤销」。 这些在 v0.2 里占了半篇幅的复杂度，全部消失了。 剩下的只有一件事：点击时把一个「在」的会话变成「活」的。

只对 host-restart 懒恢复，不碰 killed

你显式 kill 掉的会话就该是死的——它在列表里再冒出来，比消失更让人恼火。 台账里这个区分已经有了（tmux_epoch 对不上 = 机器重启带走的）， 懒恢复的候选集就是 died_reason='host-restart' 那一批， killed 的照旧只在会话历史里躺着。

03第一步：列表要显示未恢复的会话

GET /api/sessions（backend/api/api.go:185）现在只返回 tmux 活会话。 改成合并两个来源：

// 活的 ∪ 上一代被重启带走的（且原目录还在）
live     := tmux.ListSessions()
dormant  := meta.Query(`SELECT … FROM sessions
                        WHERE status='dead' AND died_reason='host-restart'
                          AND restored_from_me IS NULL`)   // 没被恢复过

// 每条带上状态，前端据此渲染
type Session struct {
    Name  string `json:"name"`
    Label string `json:"label"`
    Dir   string `json:"dir"`
    State string `json:"state"`   // "live" | "dormant" | "gone"
    Agent string `json:"agent"`   // claude | codex | ""，供 UI 显示能不能接回对话
}

这一步不做，后面全都不生效

App.tsx:334 有个 dropDeadTokens—— 「查无此会话的 id 直接丢：切机器、会话在别处被关掉，都会在这里长出打不开的空标签」。 它按 /sessions 返回的 id 表过滤。只要 /sessions 不返回休眠会话， 你上次开着的那些终端标签在 URL 还原阶段就被丢光了， 连点击的机会都没有，更到不了 §04 的钩子。

dropDeadTokens 的判据要从「是不是活的」改成「台账里还认不认得它」—— state:"gone" 才丢。

休眠会话用空心圆点和稍暗的文字与活会话区分，但不降级、不折叠、不加「已结束」这类丧气话—— 它们是随时可用的会话，只是还没启动。有对话 id 的标「可接回对话」， 其余标「点开即恢复」。原目录已不存在的（worktree 被清）判为 gone， 不进列表，只留在会话历史里。

04第二步：点击时恢复

接入点是现成的，而且只有一个。backend/pty/pty.go:314 现在是这样：

if !sessionExists(name) {
    conn.WriteMessage(TextMessage, []byte("\r\n[会话已不存在: "+name+"]\r\n"))
    conn.WriteMessage(CloseMessage, FormatCloseMessage(closeSessionGone, "session gone"))
    return
}

懒恢复就插在这一句之前——会话不在 tmux 里，先问台账认不认得它：

if !sessionExists(name) {
    // 台账里是「被重启带走的」→ 当场重开，然后照常 attach。
    // 认不得 / 是被显式 kill 的 / 原目录没了 → 才是真的 gone，维持 4404。
    if newName, ok := reviveDormant(name); ok {
        conn.WriteMessage(TextMessage, []byte("\r\n[正在恢复会话…]\r\n"))
        name = newName
    } else {
        conn.WriteMessage(TextMessage, []byte("\r\n[会话已不存在: "+name+"]\r\n"))
        conn.WriteMessage(CloseMessage, FormatCloseMessage(closeSessionGone, "session gone"))
        return
    }
}

为什么这个位置是对的

它覆盖了所有入口。点击会话列表要连 WS、从 URL 还原的旧标签页要连 WS、 手机上点开要连 WS——全都经过这里。前端几乎不用改， pty.go 注释里记的那个老问题（「昨天跑完被 kill 的会话今天还在标签条上， 于是『很多终端连不上』」）的另一半也顺手解决了：被重启带走的标签，点一下就活了。

reviveDormant 做什么

1
查台账 status='dead' 且 died_reason='host-restart' 且没被恢复过。 不满足直接返回 false，走原来的 4404。
2
查目录还在不在 os.Stat。worktree 被清是常事，没了就返回 false， 别糊里糊涂在别处建个会话（现有 restore 已经这么做了）。
3
复用 db restore 的逻辑 建会话、还名字、还目录、挂 pipe-pane 日志、记 restored_from。 这段代码已经写好了（db.go:186），抽出来共用即可。
4
有对话 id 就敲启动命令 按 agent_kind 分派（§06）。这里正是懒启动—— 只有被点开的这一个会话起 agent，其余 16 个一动不动。
5
返回新会话名，让 Handler 继续 attach 用户看到终端里打出「正在恢复会话…」，然后 agent 开始加载昨天的对话。

会话名换了，前端得知道

restore 建的是新 id 的会话（旧行保持 dead，靠 restored_from 溯源）。 所以 WS 连上之后要告诉前端「你连的这个已经改名叫 X 了」，否则标签、URL、 后续的 /api/term/<旧名> 全对不上：

// attach 成功后先发一条控制消息（前端已有 ping/pong 的 JSON 控制通道，复用它）
{"type":"revived","from":"2026-0813-1743-0012","to":"2026-0823-1102-0007"}

前端收到就把标签、terms 状态、URL 里的 token 一起换掉。 这条消息也是「恢复完成」的信号，可以顺手把列表刷一下。

并发保护：两台设备同时点同一个休眠会话

手机和桌面同时点开，两个 WS 同时进 pty.Handler， 都发现 tmux 里没有、都去 restore → 建出两个会话， 两个都顶着同一个名字、同一个目录，还都敲了 claude --resume 抢同一份 transcript。

按会话名加锁（进程内 sync.Map 的 per-name mutex 就够， Roam 是单进程），拿到锁之后再查一次 tmux——第二个请求会发现会话已经在了， 直接 attach 上去，不再走恢复。这是经典的 double-checked locking，别省那第二次检查。

05CLI 侧同一条路

ttmux attach <name>（internal/command/session/commands.go:220） 走同样的判定：tmux 里没有 → 查台账 → 是 host-restart 就恢复再 attach。 共用 reviveDormant，不要在 CLI 里抄第二份判定逻辑—— 两份必然走散，就像 AGENTS.md 开头说的那件事。

ttmux ls 也顺带把休眠会话列出来，用不同的标记：

$ ttmux ls
   ▸ memleak-hunt(2026-0823-1043-0001)  1 个窗口  08-23 10:43  [已连接]
   ◦ 拉下最新代码(2026-0813-1743-0012)  08-13 17:43  [休眠 · 可接回对话]
   ◦ /weekly-report(2026-0816-2233-001q)  08-16 22:33  [休眠 · 可接回对话]

   共 1 个会话 · 17 个休眠（attach 即恢复）

06让恢复出来的东西是完整的

记住 agent 类型

恢复时敲什么命令靠这一列，所以它是前置依赖不是锦上添花：

ALTER TABLE sessions ADD COLUMN agent_kind TEXT;  -- claude | codex | ''

建 agent 会话时（internal/command/spawn/agent.go）写上。 现有 restore 里那行是硬编码 claude --resume （db.go:229）——恢复一个 codex 会话会敲出 claude --resume <codex的对话id>。 agent_kind 为空（老数据）就只开壳、不猜：敲一条错的恢复命令比不敲更糟。

补上展示名

17 条里 11 条没有 label。以前它们躺在折叠面板里没人看见， 现在要长期显示在会话列表上，11 行裸 id 会很难受。兜底顺序： label → 首个 prompt 的前 20 字（agent 会话本来就有）→ 仓库名 · 相对路径 → 裸 id。这个兜底对活着的会话同样有价值。

竞态自然消失

db.go:229 在 CreateSession 返回后立刻 send-keys "claude --resume …" C-m，新会话里的 shell 未必已经能收键 （带 zsh 插件 / starship 的环境尤其），命令可能被吞掉开头几个字符。 懒恢复之后这段跑在用户 attach 的那一刻，而且后面紧跟着真实的 attach—— 时序比原来宽松得多。稳妥起见仍应等 #{pane_current_command} 变成 shell 再发。

这里不是 SendPromptSubmit 的场景

AGENTS.md 规定「给 TUI agent 发消息必须用 rt.SendPromptSubmit， 裸 send-keys text C-m 只打字不发送」。那条针对的是往已经跑起来的 TUI 里发 prompt。 这里是往 shell 敲一条启动命令，send-keys … C-m 是对的。别顺手「修」成 SendPromptSubmit。

07记真实的死亡时刻

这次 17 条的 died_at 全是 10:43:33——开机后第一次 Reconcile 的时刻， 不是真实结束时刻（前一晚 21:51 的 OOM 或次日 09:33 关机）。休眠会话现在要长期显示 「上次活动时间」，这个时间是错的就很显眼：

ALTER TABLE sessions ADD COLUMN last_seen TEXT;

// Reconcile 每轮给所有 live 会话刷一次 last_seen（本来就在遍历，几乎零成本）
died_at = last_seen        // host-restart：取最后一次看见它的时刻
died_at = now              // killed：Roam 在场，"现在"就是准的

顺带修一个相关的二义性：Runtime.Sessions()（runtime.go:122） 在「tmux server 没起」和「server 起着但零会话」两种情况下都返回 nil， 而 Reconcile 用 len(alive)==0 一律不动来保护后者。 这次 ttmux-web 09:37 就起来了，那 17 条却到 10:43 才被标 dead—— 就是因为 tmux server 直到你手动开第一个会话时才存在。 懒恢复不再依赖「主动开局」，所以这不再是阻塞项，但标记时刻的准确性还是靠它。

08还需要开机自启吗

需要，但目的变了：不是为了「开机做恢复动作」（懒恢复没有开机动作）， 而是为了「你打开浏览器时 Roam 已经在」。install.sh:170-194 本来就会注册 user 级 systemd 服务并 enable-linger，只是这台机器没走那条路—— 当前 ttmux-web 是 PPID=1 的裸进程（09:37:38 起，start.sh 拉的）。

切换要小心环境变量

start.sh 读 .env（口令、TOTP、TLS、绑定地址）， systemd 服务那份 Environment= 未必一致——切过去要是口令变了、端口变了， 就是把一次可靠性改造变成一次线上事故（startsh-env-overrides-dotenv 那个老坑的同一个面）。 稳妥做法：把 start.sh 包成服务的 ExecStart，环境仍从 .env 读。 一步只改「谁来拉起」，不改「拉起时带什么」。

09与 R1 的关系

R1 仍然是前置依赖，但冲突已经没了

v0.1 里这是硬约束：「一键恢复 17 个 agent = 一键复现 OOM」。 懒恢复之后，开机恢复的内存成本是 0——什么都没建。

但 R1 的每会话内存上限必须先上线：懒恢复把 agent 冷启动摊到了点击的时刻， 你连着点开 5 个会话，5 个 agent 照样一起起来。而且恢复出来的会话 必须走 memguard.Wrap——8/22 打爆机器的那个 claude 正是跑在一个这样的会话里。

10落地顺序

#动作成本拿到什么
0先上 R1 的 L1 每会话内存上限见 R1 前置依赖。点开的 agent 一样要有天花板。
1/sessions 合并休眠会话 + state 字段； dropDeadTokens 判据改为 state:"gone"一个查询 + 前端一处判据 会话「消失」的体感当场消除，且旧标签不再被丢掉。
2reviveDormant（抽出 db restore 的核心）+ pty.Handler 钩子 + per-name 锁约 120 行 + 单测 主线。点哪个哪个活。
3revived 控制消息 + 前端换名一条消息 + 一处状态更新 标签 / URL 跟着新会话走，不留死链接。
4agent_kind 列 + 按类型分派一列 + 分支 codex 会话不再被敲成 claude --resume。
5展示名兜底 + 列表休眠态样式（空心点 / 标签 / 无名分组）前端一屏 17 行里认得出哪个是哪个。
6CLI attach 走同一条路 + ls 列出休眠会话接线 命令行和 Web 行为一致。
7last_seen + died_at 取真实时刻一列 + 一次 UPDATE 休眠会话显示的「上次活动」是真的。
8补装 systemd 服务（环境变量先比对）install.sh 已有 开机后 Roam 自己在。

11验收

  • 真机重启一次（唯一诚实的测法）：开若干会话，含一个 claude 会话、一个 codex 会话、 一个目录会被删掉的 worktree 会话，然后 reboot。期望： 开机打开 Web，会话全都在列表里，此时 tmux ls 应当是空的（一个都没建）； 点开 claude 那条自动 claude --resume，codex 那条敲 codex 的命令； 目录被删的那条根本不在列表里（在会话历史里）。
  • 开机零成本：重启后不做任何操作，tmux ls 无会话、 ps aux | grep -c claude 为 0。这是懒恢复的定义，务必测。
  • 旧标签页复活：重启前开着几个终端标签，重启后直接刷新浏览器—— 标签还在（没被 dropDeadTokens 丢掉），点一下就连上。
  • 并发点击：手机和桌面同时点开同一个休眠会话， tmux ls 里只能多出一个会话，pane 里只能有一个 agent。
  • killed 不复活：显式 ttmux kill 一个会话，它不该出现在列表里， 也不该被 attach 唤醒。
  • 幂等：同一个休眠会话点开 → 关掉标签 → 再点开， 不该建出第二个会话（restored_from 已占用）。
  • 手机端：休眠态样式与无名分组在 data-size=compact 下过 web-ui-checklist 真机一遍。
