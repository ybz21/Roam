Roam · Reliability

R2 宿主重启后的会话续接

2026-08-23 早上开机，会话列表是空的——17 个连续跑了 11 天的会话一个不剩。 但它们并没有丢：台账全都记着，ttmux db restore 早就能把它们重开回来。 丢的不是数据，是那条通往数据的路。这份稿子把「消失」改成「一眼看见、一键接回」。

01先说清楚：什么能救回来，什么救不回来

tmux server 不跨重启——这是 tmux 的固有属性，不是 Roam 的缺陷。机器一关， 所有 pane 里的进程连同它们的内存现场一起消失。所以第一件事是把预期摆正：

救不回来 现场

pane 里跑到一半的进程、终端上的滚动历史、shell 的环境变量与后台作业。 进程死了就是死了，重放一段命令历史只会造出一个看起来像原来那样的假象。

救得回来 壳 + 对话

会话的归属目录、展示名、所属仓库、以及 agent 那一侧的对话 id。 agent 的上下文本来就不在 pane 里，它在 agent 自己的 transcript 里—— claude --resume <id> 接回去的是真上下文，不是模拟。

这个取舍是对的，要写进文档而不是改掉

tmux-resurrect 那一路做法（存下每个 pane 的命令行，重启后重放）在 agent 场景下是有害的： 重放 claude 得到的是一个全新的空白会话，但它占着原来的位置、顶着原来的名字， 用户以为接上了，其实上下文全没了。Roam 走「壳可恢复、现场不可恢复、对话靠 --resume 接」 这条路更诚实，也更可靠。问题不在这个取舍，在于用户根本没被告知这条路存在。

03四个缺口

G1
开机后没有任何提示 主列表空空如也，恢复入口在会话页底部一个默认收起的折叠面板里，还得先点开才去拉数据。 用户看到的就是「全没了」，除非他碰巧记得有这么个东西。这是四个缺口里唯一真正造成「消失」体感的那个。
G2
只能一条一条点 17 条要点 17 次，每次一个 toast。而且面板里混着 167 条历史，得自己从里面认出「哪些是今早那一批」。
G3
恢复出来是半成品 11 条没有 label，列表里就是一串 2026-0812-1811-000f； restore 里 agent 类型硬编码成 claude（db.go:229）， 台账压根没记这个会话原本用的是 claude 还是 codex——恢复一个 codex 会话会敲出 claude --resume <codex的对话id>。
G4
死亡时刻是假的 17 条的 died_at 全是 10:43:33——那是开机后 Roam 第一次跑 Reconcile 的时刻， 不是会话真正结束的时刻（真实是前一晚 21:51 的 OOM 或次日 09:33 关机）。 「那天下午干了什么」这个设计目标，被这一下打了折。

04G1 的解法：重启横幅

核心动作只有一个：让那批会话在开机后自己出现在眼前，而不是等用户去翻。 判据是现成的——同一个 tmux_epoch 下、died_reason='host-restart'、 died_at 同一时刻的一批，就是「上一代 tmux server 带走的」。

会话页 · 顶部（重启后首次进入）
上次重启带走了 17 个会话

2026-08-23 10:43 · 已跑 11 天 · 其中 6 个能连对话一起接回。目录和名字都还在台账里。

  • 只在有东西可恢复时出现：这批里存在至少一个目录还在的会话才显示。 目录已被删（worktree 清掉是常事）的不计数——restore 现在就会据实报错，别在横幅里许一个做不到的承诺。
  • 「不用了」是永久的：按 epoch 记一个 dismissed 标记落台账，不是 localStorage—— 换个浏览器、换台手机进来不该再被同一条横幅拦一次。
  • 恢复完自动收起，并在会话列表里把新会话高亮一下（复用现有 onRestored 的 load() + openTerm()）。
  • 手机端：横幅压成两行，三个按钮横排占满宽度，命中区 ≥44px（web-ui-checklist）。

05G2 的解法：批量恢复（必须限流）

这里是两份稿子的交汇点，也是最危险的地方

「全部恢复」如果老老实实把 17 个会话同时拉起来、每个都 claude --resume， 那就是在开机三十秒内复现造成这次事故的同一种局面—— 17 个 Node 进程同时冷启动、同时读 transcript。一键恢复会直接变成一键 OOM。

硬约束：批量恢复必须限流，且每个恢复出来的会话必须走 R1 会话内存护栏的 memguard.Wrap。不得绕过。

// POST /api/sessions/restore-batch  {ids: [...], resumeAgents: bool}
// 串行 + 小并发，逐个确认起稳再下一个。宁可慢十秒，不要一起雪崩。
const restoreConcurrency = 3
const agentStagger       = 2 * time.Second  // 两个 agent 冷启动之间的间隔

// 返回逐条结果而不是一个整体成败：17 条里第 9 条的目录没了，
// 不该让前 8 条白做，也不该让后 8 条不做。
type BatchResult struct {
    Session string `json:"session"`
    OK      bool   `json:"ok"`
    NewID   string `json:"new_id,omitempty"`
    Resumed string `json:"resumed,omitempty"`
    Error   string `json:"error,omitempty"`   // 如 "原目录已不存在：…"
}

前端用一条进度条 +「9 / 17 已恢复」，失败的留在抽屉里并标出原因，可单条重试。 CLI 侧对应 ttmux db restore --last-boot [--dry-run] [--no-resume]—— --dry-run 先打印会做什么，这种批量动作值得有个后悔的机会。

06G3 的解法：让恢复出来的东西是完整的

记住 agent 类型

ALTER TABLE sessions ADD COLUMN agent_kind TEXT;  -- claude | codex | ''

建 agent 会话时（internal/command/spawn/agent.go）顺手写上。 restore 里那行硬编码的 "claude --resume " 改成按 agent_kind 分派； agent_kind 为空（老数据）就只开壳、不猜——敲一条错的恢复命令比不敲更糟。

补上展示名

11 条没有 label，是因为 label 只在用户显式改名时才有。恢复列表里显示裸 id 等于没有信息。 兜底顺序：label → 首个 prompt 的前 20 字（agent 会话本来就有）→ 仓库名 · 相对路径 → 裸 id。这个兜底对活着的会话列表同样有价值，不只是恢复场景。

顺手修掉 restore 里的竞态

db.go:229 在 CreateSession 返回后立刻 send-keys "claude --resume …" C-m。新会话里的 shell 未必已经起到能收键的状态 （尤其带 zsh 插件/starship 的环境），命令可能被吞掉开头几个字符。 更稳的是把恢复命令作为 new-session 的启动命令直接传进去， 或者先等 #{pane_current_command} 变成 shell 再发。

这里不是 SendPromptSubmit 的场景

AGENTS.md 规定「给 TUI agent 发消息必须用 rt.SendPromptSubmit， 裸 send-keys text C-m 只打字不发送」。那条规则针对的是往已经跑起来的 TUI 里发 prompt。 这里是往 shell 敲一条启动命令，send-keys … C-m 是对的—— 问题只在时机，不在方式。别顺手「修」成 SendPromptSubmit。

07G4 的解法：记真实的死亡时刻

Reconcile 发现会话没了的时候，只能拿到「现在」。真实结束时刻要靠活着的时候留脚印：

ALTER TABLE sessions ADD COLUMN last_seen TEXT;

// Reconcile 每轮给所有 live 会话刷一次 last_seen（本来就在遍历，几乎零成本）。
// 判定某会话没了时：
died_at = last_seen        // host-restart：取最后一次看见它的时刻
died_at = now              // killed：Roam 在场，"现在"就是准的

精度取决于 Reconcile 周期（分钟级），足够回答「那天下午干了什么」。 配合 R1 的 died_reason='oom'， 台账就能同时说清什么时候没的和为什么没的——这次事故里这两个问题都得靠翻内核日志。

08要不要自动恢复

设置里给一个开关：「开机后自动恢复上次的会话」，默认关。

默认关的理由

自动拉起 17 个 agent = 一次无人值守的内存冲击，而且用户可能压根不想继续昨天那些活。 重启常常正是因为「乱了，重来」。

开了之后的约束

只恢复有对话 id 且目录还在的；上限（默认 5 个）；走 R1 的限流与内存上限； 完成后发一条通知说明恢复了哪几个。

对多数人来说，横幅上那个「全部恢复」按钮已经足够——它只比自动恢复多一次点击， 却把「要不要继续」的决定权留在了人手上。

09落地顺序

#动作成本拿到什么
1后端 GET /sessions/last-boot：返回上一代 epoch 被带走的那批 + 可恢复性 一个查询横幅和抽屉的数据源
2前端重启横幅（含 dismiss 落台账）一个组件 「消失」的体感当场消除。单做这一条收益最大。
3restore-batch API + CLI --last-boot，带限流与 R1 上限 约 150 行17 条一次搞定，且不会引发下一次 OOM
4「挑选…」抽屉一个抽屉只捡想要的那几个
5agent_kind 列 + restore 按类型分派 + 展示名兜底一列 + 分支 恢复出来是能认、能用的，codex 会话不再敲错命令
6last_seen 列 + died_at 取真实时刻一列 + 一次 UPDATE 历史时间线不再失真
7自动恢复开关（默认关）设置页一项愿意的人可以完全无感

10验收

  • 真机重启一次（这是唯一诚实的测法）：开若干会话，其中至少一个 agent 会话、 一个 codex 会话、一个目录会被删掉的 worktree 会话，重启后—— 横幅出现且数字正确；「全部恢复」后目录/名字/对话都对； 目录没了的那条报明确原因而不是静默失败。
  • 限流生效：批量恢复 10 个 agent 会话时观察内存曲线（R1 的 L3 内存条）， 不出现同时冷启动的尖峰；任一会话失败不影响其余。
  • dismiss 跨端：桌面点「不用了」，手机上进来不再出现同一条横幅。
  • 没东西可恢复时不打扰：全新环境、或上一批全部被显式 kill（died_reason='killed'）时，横幅不出现。
  • 时间线：重启恢复后查台账，被带走会话的 died_at 接近真实关机时刻， 而不是开机后第一次 Reconcile 的时刻。
  • 手机端：横幅与抽屉在 data-size=compact 下过 web-ui-checklist 真机一遍。
