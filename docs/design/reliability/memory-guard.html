Roam · Reliability

R1 会话内存护栏

2026-08-22 21:51，这台 30 GB 的机器被打爆。凶手不是 Roam 后端，是 Roam 托管的一个 Claude Code 进程——它自己涨到 15.5 GB。这份稿子先把证据摆完，再给出四层护栏： 让失控的会话只杀死自己，而不是拖走整机和另外 16 个会话。

01事故还原：内核日志说了什么

机器重启后 journalctl -k -b -1 里留着完整现场。这不是推测，是内核在被打死前 自己 dump 的进程表：

# 触发者只是恰好在申请内存的那个进程，不是元凶
Aug 22 21:51:23 kernel: buildkitd invoked oom-killer: ... global_oom
Aug 22 21:51:23 kernel: oom-kill:constraint=CONSTRAINT_NONE, global_oom,
    task_memcg=/user.slice/user-1000.slice/user@1000.service/tmux-spawn-00635c01-….scope,
    task=2.1.228, pid=831019, uid=1000
Aug 22 21:51:23 kernel: Out of memory: Killed process 831019 (2.1.228)
    total-vm:17094704kB, anon-rss:15888120kB, pgtables:31520kB

被杀的 2.1.228 是什么？

2.1.228 是 Claude Code 的版本号（本机当前 claude --version = 2.1.241，8/22 那天正是 2.1.228）。Node 应用把 process.title 设成版本串， 内核的 comm 就记成了这个。它跑在 tmux-spawn-*.scope 里—— 也就是 Roam 起的一个 tmux 会话的 pane 中。

OOM 那一刻的内存排行（按内核 dump 的真实 RSS 聚合）

2.1.228 (claude)15 516 MB
qemu-system-x864 624 MB
claude × 112 293 MB
java2 064 MB
dockerd483 MB
chrome × 8163 MB
codex × 282 MB
ttmux-web≈38 MB

结论：后端没有泄漏，护栏才是缺的那块

ttmux-web 在 OOM dump 里连前 20 都排不进（现在跑着也只有 38 MB）。 代码侧复查也支持这一点：7 处 NewTicker 全部配了 Stop()， pty.Handler 的 defer 里 ptmx.Close() + Process.Kill() + Wait() 三件齐全，PR #197 已经修掉了中心反代 每请求新建 Transport 的 goroutine 泄漏。

真正的问题是：Roam 是个进程编排器，而它编排出来的进程没有任何内存上限。 11 个常驻 claude（2.3 GB）+ 一台 AVD 模拟器（4.6 GB）+ java（2 GB）是长期底盘， 一个失控的 agent 补上最后 15.5 GB，30 GB 就没了。

为什么系统自己的兜底没救下来

机制状态为什么没生效
systemd-oomdactive 它的 ManagedOOMSwap 判据看 swap 使用率。本机 8 GB swap 在 OOM 时 USED 0B——判据永远不触发。
swap（8 GB）没用上 OOM dump 里绝大多数进程 swapents 为 0。15.9 GB anon 涨得比回收快， swap 来不及成为缓冲。
user@1000.service 内存限制未设置 没有 MemoryHigh／MemoryMax，用户切片可以一路吃到物理内存见底。
每会话限制未设置 本稿要补的主线。

02已经现成的隔离点

好消息：隔离边界早就在了，只是没上锁。本机 tmux 编译带 systemd 支持，每个 pane 自动落进一个独立 cgroup：

$ cat /proc/self/cgroup
0::/user.slice/user-1000.slice/user@1000.service/tmux-spawn-33218aea-….scope

$ systemctl --user list-units --type=scope
tmux-spawn-33218aea-….scope   tmux child pane 82485 launched by process 82284

而且 memory 控制器已经委派到了用户切片，不需要 root 就能设上限。已实测：

$ cat /sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/cgroup.subtree_control
cpu memory pids

$ systemd-run --user --scope -p MemoryMax=200M -p MemorySwapMax=0 --quiet \
    bash -c 'cat /sys/fs/cgroup$(cat /proc/self/cgroup|cut -d: -f3)/memory.max'
209715200   # 生效

这一条决定了整个方案的成本

不需要 root、不需要 docker、不需要改 tmux、不需要 systemd 单元文件。 只要在起会话时把命令包一层 systemd-run --user --scope， 每个会话就有了自己的内存天花板。

03四层护栏

四层从内到外，各自解决一个不同的失败模式。L1 是主线，其余是纵深。

L1
每会话内存上限 主防线 失控的会话撞自己的天花板，cgroup OOM 只在该 scope 内选victim。整机和其余 16 个会话毫发无损。
L2
用户切片总闸 兜底 L1 拦不住的（比如 20 个会话各自合规地占 3 GB）由软限 MemoryHigh 接住：先回收、先 throttle，不硬杀。保证 GUI／sshd／ttmux-web 还活着，人还进得来。
L3
看门狗与可见性 预防 会话列表上直接显示每个会话吃了多少。这才是「预防」——在爆之前就能看出是哪个会话在涨。
L4
事后可追溯 撞顶写进台账：died_reason='oom' + 峰值内存。下次再问「机器怎么又卡了」，答案是一行记录而不是一次考古。

04L1：每会话内存上限

改动点

唯一的建会话入口是 Runtime.CreateSession （cli/ttmux-cli-go/internal/runtime/session.go:204）。所有会话——手动开的、 agent 会话、swarm 成员、插件常驻——都从这里出去，包一层就全覆盖。

// CreateOpts 增加一个字段（空 = 用全局默认，"0" = 显式不限）
type CreateOpts struct {
    Dir, Label, Width, Height string
    Extra                     []string
    MemMax                    string // 如 "8G"；见 memguard.Wrap
}

// memguard.Wrap 把要跑的命令包进一个带上限的 transient scope。
// 包不动就原样返回——没有 systemd 的环境（容器、macOS）不该因此起不了会话。
func Wrap(cmd []string, max string) []string {
    if max == "" || max == "0" || !available() { return cmd }
    return append([]string{
        "systemd-run", "--user", "--scope", "--quiet",
        "--unit", "roam-sess-" + id,          // 可反查是哪个会话
        "-p", "MemoryMax=" + max,
        "-p", "MemorySwapMax=" + swapCap(max), // 别让它把 swap 也吃穿
        "-p", "MemoryHigh=" + high(max),       // 撞硬顶前先 throttle 一段，给看门狗反应时间
        "--",
    }, cmd...)
}

available() 的判定要便宜且可缓存：systemd-run 在 PATH 里、 XDG_RUNTIME_DIR 有值、cgroup.subtree_control 含 memory。 三条缺一就静默退回不包——护栏失效应当降级成「和今天一样」，不能变成「开不出会话」。

默认值

会话类型MemoryHighMemoryMax依据
Agent 会话（claude / codex）6 G8 G 健康态实测 180–600 MB。8 G 是 20× 余量，正常工作绝无可能撞到；15.5 GB 那种一定是失控。
普通 shell 会话3 G4 G 跑构建／测试够用；真要编译大项目由用户在设置里单独抬高。
插件常驻会话1 G2 G im-bridge、cron、hostmon 都是轻量长跑，涨上去必然是漏了。
模拟器（AVD／qemu）—AVD 内存 + 2 G 本次事故里 qemu 占 4.6 GB。上限按 AVD 配置的 RAM 推算，多给 2 G 给 qemu 自身开销。

全局默认值进设置页（docs/design/settings/），单个会话可在新建时覆盖。 设成 0 = 显式不限，给「我就是要跑个吃 20 G 的东西」留门，但那是用户明确的选择。

撞顶时会发生什么

1
先到 MemoryHigh（6 G） 内核开始激进回收并 throttle 该 cgroup。进程变慢但不死。L3 看门狗在这一刻就该发通知了。
2
再到 MemoryMax（8 G） cgroup 内 OOM。victim 只在这个 scope 里选——被杀的是失控的 agent，不是 gnome-shell、不是别人的会话、不是 buildkitd。
3
tmux pane 收到子进程退出 会话本身还在（pane 里的 shell 还活着），用户看到的是 agent 挂了，不是整台机器没了。重开一个 agent 就能继续。
4
台账记一笔（L4） died_reason='oom' + peak_rss，从 memory.peak 和 memory.events 的 oom_kill 计数读。

05L2：用户切片总闸

L1 管不了「每个都合规、加起来超了」。补一道软限，它不杀进程，只是让整个用户会话在 逼近上限时先回收、先变慢，把硬 OOM 换成可感知的卡顿：

# /etc/systemd/system/user@1000.service.d/roam-memory.conf（需 root，一次性）
[Service]
MemoryHigh=75%      # 30 G 机器 → 22.5 G，软限，触发回收+throttle
MemoryMax=88%       # → 26.4 G，硬顶，仍留 3.6 G 给内核和系统服务
ManagedOOMMemoryPressure=kill
ManagedOOMMemoryPressureLimit=60%

关键收益不是「不 OOM」，而是把 OOM 关在用户切片里。这次是 global_oom， 内核在全机范围选 victim，所以桌面才会整个僵住。限死在 user slice 之后， sshd、systemd-journald、以及跑在 system slice 的服务都还在，机器不会「卡住到只能按电源」。

顺手把 swap 用起来：vm.swappiness 现在是 60 但 swap 实际 USED 0B。 配一份 zram（压缩内存 swap，比磁盘 swap 快一个数量级）能给突发增长再争取几十秒—— 足够 L3 的通知发出去。这一条是加分项，不是主线。

06L3：看门狗与可见性

前两层是「爆了之后损失可控」，这一层才是用户问的「如何预防」：让内存在会话列表上 一直看得见，涨起来的那个自己会跳出来。

数据从哪来

不用轮询 ps 聚合进程树——cgroup 本来就按会话分好了，一次读一个文件：

$ cat .../tmux-spawn-<uuid>.scope/memory.current   # 当前占用（含子进程全部后代）
$ cat .../tmux-spawn-<uuid>.scope/memory.peak      # 历史峰值
$ cat .../tmux-spawn-<uuid>.scope/memory.events    # high / max / oom_kill 计数

会话名 → scope 的映射从 pane pid 反查 /proc/<pid>/cgroup； 用了 L1 之后 scope 名里直接带会话 id，连反查都省了。 采集挂进已有的 plugins/hostmonitor/（它已经在采 CPU/GPU/内存/磁盘/网络）， 新增一路 per-session 指标即可，不必再造一个采集器。

内存条平时是安静的细线（--ok），过 60% 转 --warn， 过 85% 转 --danger 并把整行点亮。手机端 data-size=compact 只留细线和数字，不显示分母。

通知

复用现成的 plugin_notifications 通道，两档，各自只发一次（按会话 + 阈值去重， 不然一个失控会话能刷屏）：

  • 85%——「会话 blade-os 重构 内存 6.8G/8G，还在涨」，带「去看看 / 结束它」两个动作。
  • 撞顶被杀——「会话 blade-os 重构 里的 agent 因超出 8G 被终止，峰值 8.0G」。 这条一定要有：否则用户只会看到 agent 莫名其妙没了。

不做自动 kill

看门狗不主动杀会话。硬顶交给内核（确定、及时、不会误判），看门狗只负责让人知道。 一个跑了三小时的 agent 被脚本按阈值猜杀，比 OOM 更让人恼火。

07L4：事后可追溯

sessions 表已经有 died_reason（现有取值 killed / host-restart，见 internal/sessmeta/sessmeta.go:451）。加第三种取值和一个峰值列：

ALTER TABLE sessions ADD COLUMN peak_rss INTEGER;   -- 字节，取自 memory.peak
-- died_reason 取值扩为: killed | host-restart | oom

Reconcile 判定某会话没了的时候，顺手看一眼它 scope 的 memory.events：oom_kill > 0 就记 oom 而不是 killed，并把 memory.peak 落进 peak_rss。 scope 目录随进程消失，所以这一眼得赶在 systemd 回收之前——采集器（L3）本来就在周期性读， 把最后一次读到的值缓存住即可，不必和内核赛跑。

另外把 ROAM_PPROF 这条既有的诊断口写进部署文档 （backend/cmd/pprof.go，只绑回环，默认关）。它诊断的是 ttmux-web 自身—— 这次证明不是它的锅，但下次可能是，而事故当场再去翻怎么开就晚了。

08与「会话恢复」的交汇

姊妹稿 R2 会话懒恢复 要解决「重启后会话全消失」。 它的最终方案（v0.3）是懒恢复：开机什么都不建，会话从台账渲染在列表里， 点哪个哪个才真正起来。所以开机时的内存成本是 0——早期方案里 「一键恢复 17 个 agent = 一键复现这次 OOM」的冲突，已经被设计消解掉了。

但 L1 仍然是 R2 的前置依赖

懒恢复只是把 agent 冷启动从「开机那一刻」挪到了「你点击的那一刻」。 连着点开 5 个会话，5 个 agent 照样一起起来；而 8/22 打爆机器的那个 claude， 正是跑在一个这样被点开的会话里。

硬约束：R2 恢复出来的会话必须走本稿的 memguard.Wrap，不得绕过。 落地顺序上，L1 应当先于懒恢复上线。

09落地顺序

#动作成本拿到什么
1L2 用户切片 drop-in一个配置文件，需 root 一次 立刻见效。就算别的都不做，整机也不会再被单个会话打死。
2L1 memguard.Wrap + CreateSession 接线约 120 行 + 单测 失控会话只杀自己。这是主线。
3L1 默认值进设置页前端一屏用户能按机器规格调，也能给单个会话开例外。
4L3 hostmonitor per-session 采集 + 会话列表内存条采集一路 + 前端一列 「预防」落到实处：涨起来的那个当场就看得见。
5L3 两档通知复用现有通道人不盯着屏幕也能知道。
6L4 died_reason='oom' + peak_rss一列 + 判定分支 下次「机器怎么又卡了」是查台账，不是考古。

10验收

  • 合成失控：在一个会话里跑 python3 -c "a=[];\nwhile 1: a.append(bytearray(50*1024*1024))"。 期望：该会话的 agent 在 8 G 处被杀，其他会话和桌面完全无感， 通知到达，台账记 oom + peak_rss≈8G。
  • 护栏缺失时不阻断：PATH 里去掉 systemd-run， 会话照常能建（静默降级），日志里一行说明。
  • 不误伤正常工作：跑一遍 scripts/dev/quality/check.sh full 和一次 前端 npm run build，确认 4 G 的 shell 会话上限不会把构建挤死。
  • 数据准确：memory.current 读数与 ps 对该 pane 进程树 的 RSS 求和在同量级（cgroup 会把共享页算得更准，允许有差）。
  • 手机端：会话列表在 data-size=compact 下内存列不撑破布局， 按 web-ui-checklist 过真机一遍。
