# 设计：经中心访问时，直接连到那台机器

> 状态：设计稿 + 已跑通的实测（本文所有数字都是 2026-09-09 在真中心 / 真节点上量的）。
> 关联：[P2P 直连传输](./p2p-direct-transfer.md)（frp 时代的原始设计）、
> [通用传输实施计划](./general-transport-plan.md)、[多机架构](../cluster/architecture.html)。
> 先看 §2 的四行表，那是这件事全部的理由。

## 1. 问题

中心（Broker）模式下，浏览器打开的是中心，所有业务请求都经 `/n/<nodeId>/*` 反代进节点的
yamux 隧道：

```
浏览器 ──HTTPS──▶ 中心（阿里云，1.6G 内存 / 带宽受限）──wss+yamux──▶ 节点（家里/机房，NAT 后）
```

终端的每一次回显、镜像的每一帧、文件的每一个字节，都在中心那台机器上过一遍。它既是延迟的
放大器，也是带宽的瓶颈——而且是**唯一**要花钱的那一段。

而 P2P 直连（pion + WebRTC DataChannel）在仓库里已经有了：PR #121 合入，信令
`/api/p2p/signal`、control / media / file 三类 PeerConnection、文件下载与两种镜像都已经
接上去。但它是**在 frp 时代设计的**（2026-07），比多机（#187，2026-08）早一个月：
从没有人验过它在中心模式下还成不成立。

这份文档回答的就是那个问题：**从中心进来的浏览器，能不能绕开中心、直接和那台具体的机器建链。**

## 2. 结论：能，而且今天就已经能

先给答案。下面四行是同一台 Jetson、同一份 20MB 文件、同一次会话里量出来的：

| 路径 | 20 MB 用时 | 吞吐 |
| --- | --- | --- |
| 经中心中转（浏览器 → 阿里云 → Jetson，今天所有流量走的路） | 52–67 s | **0.30–0.38 MB/s** |
| P2P 直连 DataChannel（信令过中心，数据不过）· echo 往返 | 7.8–8.4 s | 4.7–5.1 MB/s（线上）· 2.4–2.6 MB/s（单向等效） |
| 局域网直连 HTTP（同一份文件，不经任何中转）——直连的天花板 | 1.2 s | 16.6 MB/s |
| P2P 直连 DataChannel · 同机节点（排除 Jetson 的 ARM CPU 影响） | 0.5 s | **80.6 MB/s**（线上） |

（两组数字是同一份脚本跑两轮的区间，不是取最好的那次。）

控制面同理。`/api/me` 一个来回：

| 路径 | RTT |
| --- | --- |
| 浏览器 → 中心 → 节点（今天） | 72–101 ms |
| 浏览器 → 节点（局域网直连） | 12–58 ms |

**不需要新协议，不需要改信令**。`/api/p2p/signal` 是普通的 WebSocket，中心的
`ProxyNode` 本来就会把 WS 升级原样转发进隧道；SDP 与候选跟着走，数据面则完全不碰中心。
实测（§3）：中心返回 `101 Switching Protocols`，两台节点都建成了直连，左边栏亮起
「直连 · 局域网」。

要做的事只有三件，一件比一件贵：

1. **把开关打开、把建链等待砍掉**（今天要等 30 秒，见 §3.3）——纯前端 + 配置，最贵的收益。
2. **中心统一下发 ICE 配置，并自己当 STUN**——每台节点各配一份 `p2p_ice_servers` 不可运维。
3. **中心自己当 TURN 兜底**——在 frp 时代 TURN 被否决过（要花带宽钱）；**在中心模式下这条
   理由不成立**，因为那份带宽今天本来就在花，见 §4.2。

## 3. 实测记录（2026-09-09）

环境：中心 = 阿里云 `47.94.183.77:13570`（`roami-hub.service`，v0.2.0-rc.1）；
节点 = 「开发机」`n_c2dcd22f…`（x86，与浏览器同一台）与「Jetson」`n_992b4668…`
（ARM，同局域网另一台）。浏览器 = 真 Chrome（playwright 驱动，脚本见
`scripts/dev/p2p/hub-link-probe.mjs`）。两台节点都临时 `p2p_enabled: true`。

### 3.1 信令穿中心：通

```
$ curl -k -i --http1.1 -b <hub cookie> -H 'Connection: Upgrade' -H 'Upgrade: websocket' … \
    https://47.94.183.77:13570/n/n_c2dcd22f…/api/p2p/signal
HTTP/1.1 101 Switching Protocols
```

中心不认识 P2P，也不需要认识——它只是把这条 WS 转发进隧道。节点侧收到的是隧道流，
`cluster/node` 把它标成 `auth.WithInternal`，于是节点直接认「中心已经替我校验过用户」。
**鉴权模型不用动**（这一条很重要，见 §5）。

### 3.2 数据面直连：通

开发机（与浏览器同机）：

```
选中候选对  host/udp ↔ host/udp 192.168.130.19:39377   RTT 0ms   已收发 1362/1314 字节
左边栏      直连 · 局域网
```

Jetson（另一台机器）：

```
选中候选对  prflx/udp ↔ prflx/udp   RTT 2ms
```

RTT 2 ms 就是证据本身：经中心那条路是 72–101 ms，2 ms 只可能是局域网直连。

### 3.3 但要等 30 秒——今天最大的问题

同一次连接的候选时间线：

```
+157ms   gathering=gathering
+201ms   candidate … typ host   （…​.local 45647）
+256ms   candidate … typ srflx  （39.155.137.50 45647）
+30255ms gathering=complete
+30255ms (end-of-candidates)
```

**能用的候选 0.26 秒就齐了，链路却在 30 秒后才建起来。** 原因是 PR #121 评审 P0-2 把
trickle 改成了非 trickle（双向 trickle 有候选竞态，跨网 srflx 会丢），于是前端
`waitForIceGathering` 死等 `iceGatheringState === 'complete'`，而 Chrome 要把所有网卡、
所有 STUN/TURN 的超时都跑完才置 complete，上限正好就是我们配的 30 秒
（`p2pGatherTimeoutSec`，为了慢网手机蜂窝的 srflx 才调到 30 的，见 85f9f1f）。

在 frp 时代这是「每次下载慢 30 秒」；在中心模式下 control PC 是全局链路，这 30 秒
**决定了整个会话前 30 秒都在中转**。这是第一优先要修的。

### 3.4 中心那台机的 UDP 入站是封的

在中心上起一个最小 STUN 应答器，从外面打：

```
47.94.183.77:13571 → 超时          （新端口）
47.94.183.77:13570 → 超时          （已经开着 TCP 的那个端口，UDP 仍不通）
```

阿里云安全组只放了 TCP。**「中心自建 STUN/TURN」这条路的前置条件是先去控制台加一条 UDP 规则**
——这件事只有账号主人能做，代码改不动它。

顺带验了公共 STUN 在这条网络上其实是通的（`stun.l.google.com:19302` 正常返回
XOR-MAPPED-ADDRESS），所以 §3.3 那 30 秒不是「STUN 打不通」，纯粹是等 gathering complete。

## 4. 方案

### 4.1 分层：一条路不通就换下一条，最后一条永远是今天这条

```
① host / 局域网直连        免费   同网时天然成立（已实测）
② srflx（STUN@中心）        免费   跨网打洞的主力；要中心开 UDP 入站
③ TURN@中心                 与今天等价的带宽   打不通洞时的中转，但走 UDP、不过 HTTP 代理
④ 隧道中转（今天这条）      不变   ①②③ 全废时行为与现在一模一样
```

第 ④ 层不是「兜底」而是「地板」：P2P 全线失败时，用户看到的就是今天的 Roami，
一个字节的行为差异都没有。这也是 P2P 能默认打开的前提。

信令永远走 ④——它只有几 KB，而且必须在数据面还不存在时就能用。

### 4.2 为什么中心模式下 TURN 从「否决」变成「该做」

原始设计里 TURN 被明确否决，理由是「零带宽成本约束下不建 TURN」。那个判断在 frp 时代是对的：
frps 上跑 TURN = 白白多花一份带宽钱，而 frp 那条路本来就能传。

中心模式下这个前提翻转了：**那份带宽今天已经在花了**——0.30 MB/s 的中转就是中心在掏。
TURN 中转同一份数据，带宽账单一模一样，但：

- 走 UDP，不再经过 `httputil.ReverseProxy` + yamux 流 + TCP 队头阻塞；
- 中心不再需要为每条业务流维护一对 goroutine（2026-08-11 那次 goroutine 泄漏就是这么来的）；
- 拥塞控制在 SCTP 上，大文件不再和终端抢同一条 TCP。

所以 TURN 在这里不是「新的成本」，是「同样的成本换一条更好的路」。**但它必须是最后一档**：
默认关、只在 ①②失败后按需申请，且凭证短期（HMAC + TTL 10 分钟，coturn REST 那套约定），
免得中心变成一个开放中继。

### 4.3 ICE 配置由中心下发，不再每台节点各配一份

今天 ICE 服务器来自节点自己的 `p2p_ice_servers`（默认 `stun.l.google.com`）。二十台机器
就是二十份配置，改一次 STUN 要挨台改——而且节点根本不知道自己是从哪个中心被访问的。

改成中心出这份配置：

- 新增 `GET /api/hub/ice` → `{ iceServers: [{urls:[stun:…]}, {urls:[turn:…], username, credential}] }`，
  TURN 凭证按请求现签（短期）。
- 前端在中心模式下**优先**用它；单机模式下行为不变，仍读节点的 `/api/p2p/config`。
- 节点侧那份配置保留，作为「直连节点局域网口」时的来源。

### 4.4 建链要在候选够用时就发，不等 gathering complete

保留非 trickle（不退回 trickle，那个竞态是真的），但把「等完」换成「等够」：

- 收到第一个 `srflx` 候选后再宽限 500 ms 就发 offer；
- 一个 srflx 都没有但已有 host 候选时，宽限 1.5 s 后发（同网场景不该为公网候选买单）；
- 硬上限仍是 `p2pGatherTimeoutSec`（默认 30 s），慢网蜂窝那条路不受影响。

按 §3.3 的时间线，这一改把建链从 30 s 压到 ~0.8 s。

### 4.5 链路要跟着「当前机器」走

`startControlLink()` 的 effect 依赖只有 `[authed, prefs.p2pEnabled]`，链路建在**调用那一刻的
当前节点**上。今天不出错，只是因为两个换机器的入口（`App.switchNode`、`HubPage`）都
`location.reload()` 了——正确性挂在一个副作用上。

要做的事很小但必须做：把 `currentNodeId` 纳入依赖，切换时先 `stopControlLink()` 再重建；
`connect(service)` 在 label 里带上 nodeId，节点侧对不上就拒。否则哪天换机器改成软切换
（不刷新），镜像和文件就会从上一台机器上来，而界面显示的是这一台——最难查的那种错。

## 5. 安全

数据面绕过中心，等于中心失去了对这条流的可见性与随时掐断的能力。这不是新增风险，但要说清楚
边界：

- **授权发生在建链那一刻**，不在每个请求上。中心校验用户会话 → 转发信令 WS → 节点按
  `WithInternal` 放行。所以将来若要做「用户 A 只能访问节点 X」，判定必须落在
  `ProxyNode` 转发信令之前，而不是某个业务 handler 里。
- **DTLS 指纹绑定**：SDP 里的指纹经由已鉴权的信令通道交换，第三方即使知道候选地址也建不起
  DTLS，所以「数据面没有 cookie」不构成漏洞。
- **节点内网 IP 会出现在 SDP 里**，中心与浏览器都看得到。自己的机器，可接受；但如果将来
  中心要托管别人的节点，这条要重新评估（pion 侧 `SetICEMulticastDNSMode` 目前是
  QueryOnly，即节点播报真实 LAN IP，这是同网直连能成的原因）。
- **TURN 凭证必须短期**，且只对已登录会话签发。

## 6. 落地顺序

每一阶段单独可验、可回退，且都不改变 P2P 失败时的行为。

**M1 · 让它现在就好用**（前端 + 配置，无新服务）
- §4.4 候选够用即发；§4.5 链路跟随当前机器。
- `p2p_enabled` 从「每台机器手改 yaml」改成中心模式下默认开（用户偏好仍可关）。
- 验收：中心里打开任一节点，左边栏 1 秒内亮「直连」；关掉偏好后行为与今天逐字节一致。

**M2 · 中心当 STUN + 统一下发 ICE**（后端小改 + 一条安全组规则）
- 中心内置 STUN（pion，几十行；与 13570 共存于另一个 UDP 端口）；`GET /api/hub/ice`。
- 前置条件：阿里云安全组放通该 UDP 端口（§3.4，只有账号主人能做）。
- 验收：节点日志里出现来自中心 STUN 的 srflx 候选；断开公共 STUN 仍能建链。

**M3 · 跨网真验**（没有代码，纯测量，但必须做在 M4 之前）
- 手机蜂窝 / 异地网络各测一轮，记录成功率与失败时的候选类型。
- 已知的坏情况：CGNAT + 双方都无公网 IPv6 = 零成本无解（9109ea4 在 frp 时代就实测过）。
  M3 的意义是量出这种情况占多少，决定 M4 值不值。

**M4 · 中心当 TURN**（仅当 M3 显示直连率不够）
- pion/turn，短期凭证，带宽计入中心页指标（`/api/hub/self` 已有 requests/tunnels，加一项）。

**M5 · 终端搬上直连**（收益最大、风险也最大，放最后）
- 中心模式下键盘回显 72–101 ms → 12–58 ms。终端是可靠有序流，断链回退必须无缝，
  所以要等前面几阶段把链路稳定性证明了再动。

## 7. 还没有答案的

- **真跨网没验**。本轮所有直连都是同局域网（浏览器与节点在一张网里）。中心模式最有价值的
  场景恰恰是「人在外面、机器在家里」，那一档的成功率现在是**未知**，M3 就是为它准备的。
- **Jetson 那 4.7 MB/s 是谁的锅**：同一套代码在 x86 同机节点上跑到 80.6 MB/s，说明瓶颈不在
  DataChannel 本身，更像 ARM 上 pion 的 SCTP/DTLS 开销或那条百兆链路。要拆开量。
- **中心 1.6 G 内存能扛多少条 TURN 中继**：没测。M4 之前要有数。

## 8. 怎么复现本文的实测

```bash
# 1. 节点上打开开关（两台都要）：~/.roami/config.yaml 加 p2p_enabled: true，重启 roami
# 2. 建链探针：登录中心 → 指定节点 → 打印候选时间线与选中的候选对
HUB=https://<中心> NODE_ID=<节点id> HUB_PW=<中心口令> node scripts/dev/p2p/hub-link-probe.mjs
# 3. 吞吐对照：直连 echo 往返 vs 经中心中转的 HTTP 下载
HUB=https://<中心> NODE_ID=<节点id> HUB_PW=<中心口令> MB=20 node scripts/dev/p2p/hub-link-bench.mjs
```

两个脚本都不写任何密钥，口令只从环境变量读。
