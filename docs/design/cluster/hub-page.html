中心页：让中心自己能被看见

今天中心卡死了十几个小时，是部署时碰巧撞见的 —— 界面上没有任何地方会说「中心不健康」。 这份稿子补的就是这个洞：中心自身的状态、它接着哪些机器、怎么再接一台，以及**出事时它自己会喊**。

01 为什么中心不该进「切换机器」

先说一个不做的决定，它决定了后面所有形状。

中心不跑会话、项目、文件、终端——它只做路由、注册表和控制台。把它当作切换器里的第 N 台机器， 意味着切过去以后大半个应用是空的：会话页 0 条、文件页没有根、终端开不出来。那不是「另一台机器」， 是「另一种东西」。

所以：机器列表照旧只列节点，中心单独一条入口，用分隔线隔开。 它的语义是「去看中心」，不是「把浏览范围切到中心」——点它进 #/hub，当前机器不变。

切换器长这样

开开发机5ms
JEJetson29ms
中中心 2 台在线

正常态：中心那条只是多一个入口，安静地待在分隔线下面。

开开发机5ms
JEJetson离线
中 中心 内存持续增长

异常态：这一条变红，侧栏那枚按钮上也带一个红点——见第 4 节。

03 数据从哪来：/api/hub/self

现在中心只暴露 nodes / bootstrap / enroll， 没有一个接口回答「中心自己怎么样」。加一个。

字段来源为什么要它
version / startedAt编译期 + 进程启动「重启过没有」——今天要不是我去 ssh，根本不知道它已经重启了几次
rssBytes/proc/self/status泄漏第一眼就看得出来
goroutinesruntime.NumGoroutine()今早的元凶：19185。RSS 涨得慢，goroutine 涨得早
heapBytesruntime.MemStats跟 RSS 分开看，能区分「真占着」还是「没还给系统」
tunnels注册表里活着的 session 数节点在不在，与「注册过几台」不是一回事
samples[]进程内环形缓冲（5 分钟一采，留 24h）曲线才是证据。单点数字看不出「稳在 20」还是「正在爬」
采样放进程内，别再靠 cron。 现在那份 health.log 是我昨晚在服务器上手写的 cron + curl， 换台机器就没有了，重装一次就丢。放进程里，任何一台中心都自带这条曲线。
诊断口不进这个接口。 pprof 仍然只绑回环（ROAM_PPROF），页面上那个「看诊断」按钮只教你 ssh -L 怎么转发。把 heap/goroutine dump 挂到公网接口上，等于把内存内容和打垮进程的入口一起送出去。

04 光有页面救不了今天这种事

这一节是整份稿子里最要紧的。

今天中心卡了十几个小时。就算当时这个页面已经存在，也没人会去看它——你只有在「发现打不开」之后 才会想起有这么一页。所以异常必须自己冒到眼前：

  • 侧栏那枚按钮上的红点。它常驻在每一页，是唯一能保证被看见的位置。
  • 切换器下拉里那条中心变红，写一句人话的原因（「内存持续增长」而不是「rss=299MB」）。
  • 点进去才是这一页的详情与动作。
但阈值现在不该拍脑袋定。 「内存 > 300MB」在今天这台 1.6G 的机器上合理，换台 16G 的就是误报； 「goroutine > 1000」在两台节点时合理，接了二十台就不一定。建议先攒一周曲线再定—— 在那之前只做「有曲线可看」，不做告警。误报一次，这个红点以后就再没人信了。

05 落地顺序

阶段做什么为什么这个顺序
P1/api/hub/self + 进程内采样没有数据，页面就是个空壳。先让数据存在
P1中心页 + 切换器里的入口把已经有的 nodes / enroll 一并搬进来，设置页那张 HubSelfCard 只留配置
P2三个不依赖阈值的信号 + 侧栏红点先上不会误报的那几个，让红点从第一天起就可信
P3基于一周曲线的阈值告警数据说话，别拍脑袋
顺带一个已经验证的结论：今早那个 goroutine 泄漏（每请求 new 一个 Transport）修完后， 线上 goroutine 从 19185 掉到 18–21，并且**会随 IdleConnTimeout 回落**（观察到 50 → 18）。 这一页要展示的曲线，正是能让这类结论一眼可见的东西。
