多机：两种模式，页面上就能切

0. 只有两种模式，用一句话各自说清

多机这件事最容易卡住的地方，是用户第一次打开时不知道「我这台该配成什么」。 所以设置页第一屏不给表单，先给两张卡片让人选身份；选完才出现那一种模式真正需要填的东西。 文案里不出现 standard / cloud / frps / frpc —— 那是实现的说法，不是用户的说法。

一条要反复讲的事：接入中心不会关掉局域网直连。同一台机器永远有两条路—— 在家/公司用局域网直连（快、不过中心），在外面走中心。所以「要不要接中心」不是一个取舍题， 接了只多一条路。设置页里把这两条并排画出来，就是为了让人不必问这句。

3. 中心怎么来、要配什么

上一节把「中心」这一屏画出来了，但漏了更前面的一个问题：中心是怎么诞生的， 它自己又要配什么。今天的实现里这块是空的——切成中心之后那一页只有机器列表， 而中心至少有一样东西必须能配，不配就会静默地坑人（见下 §3.2）。

3.1 三条路各服务一种人，都得留

已经有一台 Roam
最常见 · 想先试试
在那台机器上打开设置 › 多机，把角色改成「中心」，重启。 它原来的项目和终端会停掉——所以这条路适合本来就闲着的那台。
新买一台小主机
推荐 · 长期用
装的时候就说清楚它是中心，装完直接是入口，不经过「先当机器再改成中心」那一步。
curl -fsSL https://roam.sh/install.sh | bash -s -- --hub
丢进容器
已经有 docker 的人
中心不跑业务，没有 tmux / Chrome / adb 那些依赖，是这套里唯一适合塞进容器的角色。
docker run -d -p 443:13570 \
  -v roam-hub:/root/.roam \
  roam/hub
为什么「装的时候就选」值得单独做一条：走第一条路的人得先看着一台机器把自己的终端和项目 关掉，心里是发怵的——而买台小主机当中心的人，那台机器上本来就什么都没有， 让他先经历一遍「变成机器、再改成中心」纯属多余。

3.2 中心只有一样东西必须配：对外地址

中心不知道自己在外面叫什么。它看到的是网卡上的内网地址（云主机上常是 172.17.x），而机器要拨过来用的是公网地址或域名。今天的实现是拿 「你此刻浏览用的那个 Host」去拼接入命令—— 你在局域网里管中心，生成的命令就带内网地址，外网那台机器照着做必然连不上， 而且失败信息里完全看不出是这个原因。

中心的对外地址机器和浏览器都用它

  • 这条校验是纯本地的、能立刻做：地址解析出来落在 RFC1918 / localhost / .local 就提示。不用探测外网可达性——那件事中心自己做不到， 而这条静态判断已经能挡住绝大多数「照着命令做却连不上」。
  • 「用当前地址填」是个按钮，不是默认行为：默认值给一次就行，之后用户改过就别再覆盖他。
  • 令牌有效期放在这里而不是「添加机器」弹窗里：它是中心的策略，不是某一次添加的参数。

3.3 中心不需要配、但用户会问的几样

问题 答案 · 以及界面上摆在哪
谁能接进来？ 只有拿到令牌的。令牌一次性、有有效期、只能你在控制台里签。 不做「申请—审批」那一套：单用户场景下，能登进中心的人就是能签令牌的人，多一层审批只是多一步。 团队版再说
中心要不要开 TLS？ 要，而且它比单机时更要紧——中心是唯一暴露在公网的那一台。 沿用现有的 TLS 设置（默认自签），不在多机页里再放一份开关； 但要在这一页提醒一句「你正暴露在公网」， 这是单机时不存在的处境
中心存了什么？ 只有机器名单和凭证哈希（<home>/cluster/nodes.json）。 你的代码、文件、会话都不落在中心上，它只转发。 这句话要写在中心页上——不写，用户会以为把代码同步到了公网机器
中心挂了会怎样？ 外网访问断，局域网直连照常，机器上跑着的活一点没事（tmux 在各自机器上）。 中心恢复后机器自动重连。这句同样该写在页面上，它是这套架构最让人安心的一点
中心自己能被管理吗？ 不能，中心不是一台「机器」——它不在机器列表里、没有终端和文件。 想管它就 ssh 上去，或者把它改回「这台机器」
实现状态：① 已做——cluster.public_url 配置项 + 接入命令用它， 内网地址当场提示（纯本地判断，见 isPrivateURL）；② 已做—— cluster.enroll_ttl_min，默认仍是 30；③ 已做——那两句印在中心那张卡上。 还缺：④ install.sh --hub 与容器镜像。

4. 初次安装：只问一次，而且能一键跳过

装的时候不问身份。install.sh 默认装成「这台机器」——命令行是问这个问题 最差的时机：用户还没见过界面，不知道自己在选什么，选错了还得回来重装。 唯一的例外是他自己知道要装中心（--hub），那说明他已经想清楚了。

问题留到第一次打开网页——今天那里已经有一步「设置登录口令」，多机这一问接在它后面， 只多一屏，而且默认选中第一项，回车即过。绝大多数人第一次装就是单机自己用， 对他们来说多问一句都是负担。

5. 后续更改：四种起点，各自会发生什么

改身份不是一个开关那么简单——每一种转移丢的东西不一样。只有真会丢东西的方向才拦， 其余的直接做，别为了"一致"给每一步都加确认框。

从 → 到会发生什么 要重启？要拦一下？
单机 → 接入中心
最常见		 多起一条到中心的出站长连。本机什么都不变——终端、项目、局域网直连全在， 只是多了一条外网进来的路 要
隧道客户端在启动时建		 不拦。没有任何东西会丢，拦了只是碍事
接入中心 → 断开 外网访问没了，局域网直连照常。中心那边的记录还在，重新接入要一张新令牌 （旧的是一次性的） 要 轻拦一句：说清「要新令牌才能再接回来」——用户以为随手能撤销，其实不能
这台机器 → 中心
破坏性		 这台不再跑活：终端会话断开（tmux 会话本身还在），项目、文件、Git、镜像 都不再出现在界面里。它变成入口 要 要，而且要列清单：几个会话会断、哪些东西会从界面消失。 文案说的是会失去什么，不是「切换 cluster.mode」
中心 → 这台机器 重新开始跑自己的活。接进来的机器失去入口，直到你把它改回中心或另起一个 要 要，但理由不同：丢的不是这台的东西，是别人的入口。 提示里要写「3 台机器会失去入口」
换一个中心 断开旧的、接入新的。旧中心那边这台机器变离线，但记录还在 要 不拦，但要提示「旧中心那边记得把它移除」——否则那边会挂一台永远离线的机器
「要重启」这件事本身要说清楚。五种转移全都要重启，因为 hub 与 standard 的依赖图不同、隧道客户端也只在启动时建—— 这不是能热切的东西。所以统一做成「保存 → 自动重启 → 页面等它回来」： 前端保存后轮询 /api/version，回来了就自己刷新。 并且要说一句「如果没回来，去那台机器上手动启动一次」—— 没有 systemd 之类守护的装法，进程退出就真的退出了。

6. 切模式的确认框长什么样

把这台机器改成「中心」？
改成中心之后，这台机器就不再跑活了：
  • 正在跑的 4 个终端会话会断开（tmux 会话本身还在，重新切回来还能接上）
  • 这台机器上的项目、文件、Git、镜像都不会再出现在界面里
  • 它会变成入口：别的机器接进来后，你在这里访问它们
需要重启服务，大约 3 秒。
  • 只有 这台机器 → 中心 需要确认，反过来不用：切回「这台机器」只是把本机能力重新打开， 没有东西会消失。确认框只留给真会丢东西的方向。
  • 文案不说「切换 cluster.mode」，说的是用户会失去什么——终端会断、项目会不见。 这是他唯一需要判断的信息。
  • 写清「tmux 会话本身还在」：不写这句，用户会以为把活干没了， 而实际上只是这台机器不再从这个界面暴露而已。

8. 落地要点

  • 后端要一对新接口：GET /api/cluster/config 返回当前模式 + 中心地址 + 名字 + 分组 + 实时状态（已连接 / 重连中 / 最后一次失败原因）；PUT 写回 config.yaml 的 cluster: 段。令牌只写不读——读回来没有意义，还多一个泄漏面。
  • 「最后一次失败原因」直接用节点侧已经翻好的那句：令牌过期 / 凭证失效 / 地址不是 中心， 三种的下一步完全不同。这句话现在只进日志，得让它进界面。
  • 改模式要重启服务：cloud 与 standard 的依赖图不同（中心根本不构造业务 runtime）。 所以是「保存 → 重启 → 页面自己重连」，不是热切换。前端保存后轮询 /api/version 等它回来。
  • 写 config.yaml 要保留注释：现有的 SavePassword 是正则替换单行， 整段 cluster: 得同样按行改写而不是 yaml.Marshal 全量重写—— 后者会把模板里那些解释性注释全部抹掉，而那些注释是用户手改时唯一的说明书。
  • i18n：整页文案走 t()，两份 locale 同步。模式名在英文里用 This machine / Hub——同样不用 standard/cloud。
