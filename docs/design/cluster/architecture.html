Roam · Cluster · 技术架构 v0.2

多机管理 —— Broker / 节点 / 隧道 · 协议选型与带宽账

0. 一分钟看懂

心智模型是 frp：云端 Broker ≈ frps（唯一公网入口，只转发不跑业务）， 标准节点 ≈ frpc（在 NAT 后主动出站拨号注册进来）。 区别是把这套内建成产品能力——用户不用手配隧道，且能在一个界面里切换所有机器。 同一个二进制两种模式，角色由配置决定；默认 standard 且不填 broker 时， 行为与今天的单机完全一致。

后端主链路 已经写完并有集成测试（PR #116，1036 行）：配置、yamux over wss 隧道、 注册表、enrollment、反代、节点侧出站客户端、内部主体鉴权。 它落后 main 93 个提交且已冲突，且有三处硬伤要修（§3）。 前端一行没写——这一期真正的工作量在那边（§5、§6）。

协议问题的结论（§10、§11）：承载没有比「WebSocket + 复用」更稳的标准选择， 行业路径都是先 TCP+复用跑通、再迁 QUIC（frp / Cloudflare Tunnel 都走过这条）， 所以 P1 不动、但要先抽出 Transport 接口并按流量分三条隧道（否则一次大下载会卡住终端）。 搜索和工作台的行动队列必须是跨机器的（§12）——它们是多机之后仅有的「功能变强」的地方， 而且它反过来要求 SearchHit.id 在 P1 就带上 nodeId，晚做是全面返工。 真正的带宽大头不在隧道协议上，在镜像：今天浏览器与手机镜像都是整帧 JPEG， 一路标清 6 Mbps ≈ 2.7 GB/小时，换成视频编码能省 5–10×，这比换任何承载协议都值钱。

1. 形状：一个二进制，两种模式

模式含义谁跑业务谁监听公网frp 类比
standard
默认		 现在的 Roam，跑全套能力。可选填 cluster.broker → 额外出站注册进云端 本机本机（局域网直连口保留）frpc（填了 broker 时）
cloud 云端 Broker：注册表 + 隧道 + 反代 + 控制台静态资源 不跑（只转发）是（唯一公网入口）frps

没有第三种「client 模式」：一台开发机注册进云端后，它本身还是标准 Roam， 只是多连了一条到 Broker 的隧道。 "Client" 只是「标准节点在云端视角下的身份」，不是一种部署形态。

两条入口并存，不是二选一

这是硬要求，不是副作用：上了云之后，本机监听口照常对外。同一台机器同时有两条路——

经 Broker公网 / 跨网
https://broker/n/<id>/api/…
直连同一局域网
https://192.168.x.x:13579/api/…
两条都要登录直连走本机 public handler（Cookie）， 隧道走 Broker 校验后的内部主体。没有一条是免密的
  • 为什么必须并存：局域网直连没有 Broker 那一跳，延迟低一个量级、带宽是本地网速， 还在公网/Broker 挂掉时仍然能用。为了上云去掉它，等于用一个远程依赖换掉一条本来最好的路。
  • 实现上就是「什么都不做」：standard 模式照常 r.Run(bind)， 隧道客户端只是另起一个 goroutine 拨出去。同一个 http.Handler 两个入口， 业务代码一行不改。
  • 前端跟着自适应：nodePath() 在没有 currentNodeId 时返回裸路径 （§5）。所以浏览器直接开 192.168.x.x:13579 时，界面自动退回单机形态—— 没有机器芯片、没有方章、没有 /nodes。同一份前端，两种入口，零分支。
  • 一台机器可以同时被两个人从两条路用：tmux 本来就是多客户端的，这不引入新问题。

三处必须修的硬伤

① 反代重写路径时丢掉了 RawPath，含特殊字符的文件路径会 404
现在是 c.Request.URL.Path = c.Param("path")——Param 给的是已解码的值， 赋回 Path 后 RawPath 被清空，转发出去时按默认规则重新编码。 我们的 /api/file/serve/*path 把绝对路径塞进 URL，文件名里的 # ? % 空格全都会在这一跳变形，preview / 下载直接 404。 正确做法是按前缀截断而不是重建： 
prefix := "/n/" + url.PathEscape(id)
r.URL.Path = strings.TrimPrefix(r.URL.Path, "/n/"+id)
if r.URL.RawPath != "" { r.URL.RawPath = strings.TrimPrefix(r.URL.RawPath, prefix) }
并给这条加一个用例：文件名 a b#c%d.txt 经代理后仍能读到内容。
② bootstrap.recommended 现在返回「第一个在线节点」，这不是用户想回到的那台
用户想回到的是上次用的那台，而那个值只有浏览器知道。所以：recommended 只作为兜底（localStorage 为空或指向的节点已不存在时才用），并且把「上次用的」 存进 Broker 级偏好 /api/broker/preferences 以便跨浏览器同步（异步、失败不阻塞）。 详见 §7 的启动顺序。
③ 没有延迟测量，而 UI 的每一处都要显示 12ms
心跳是节点单向上报（{sessionCount, load}），拿不到 RTT。 改成控制流上的 ping/pong：Broker 每 5s 在控制流发一个带序号的 ping， 节点原样回；Broker 记录 RTT 的 EWMA 写进注册表。 顺带解决心跳判活的方向问题——现在节点不上报就"看起来活着"直到超时， 有了 Broker 主动 ping，掉线在一个 ping 周期内就能发现。

4. 路径契约

只有一种寻址方式：稳定路径前缀 /n/<percent-encoded nodeId>/…。 它同时适用于封装请求和浏览器原生发起、加不了自定义 header 的资源请求 （<img src>、<iframe>、<a download>、window.open、WebSocket）。 禁止靠 header 注入节点身份——那条路在原生资源请求上根本走不通， 而且给了伪造的口子。

/api/broker/preferencesBrokerBroker 级偏好（当前节点、弱联动开关）。不是节点业务偏好

nodeId 是不可变内部身份，显示名永不参与寻址。名字可以重命名、可以重复， 参与寻址就等于给"删错机器"留了后门。路径里的 nodeId 逐段 percent-encode， Broker 解码后按精确 ID 查注册表，不做显示名回退。

// 单机与多机同一份代码：没有 currentNodeId 时返回今天的路径，一个字节都不差。
// 这就是「单机零变化」在实现层面的保证——不是靠两条分支，是靠一个恒等式。
export function nodePath(path: string): string {
  const id = currentNodeId()            // null = 单机 / 直连节点
  return id ? `/n/${encodeURIComponent(id)}${path}` : path
}
export const nodeApi = (p: string) => nodePath('/api' + p)
export function nodeWs(p: string): string {
  const proto = location.protocol === 'https:' ? 'wss' : 'ws'
  return `${proto}://${location.host}${nodePath('/api' + p)}`
}
验收靠 lint，不靠自觉。加一条 ESLint 规则（或复用 hover:check 那种脚本审计）： frontend/src 里不允许出现字面量 '/api/'，除了 cluster/node-url.ts 自己。 这类"盘点一遍改完"的任务，漏一处的表现是"某个文件预览在多机下 404"—— 几个月后才有人踩到，那时候已经没人记得盘点表了。

7. 启动顺序与首帧

currentNodeId 绝不能放进节点侧的 /api/preferences—— 那会形成启动死循环：要读偏好得先知道去哪台机器读。它属于 Broker 级状态。 

1. 读 URL 的 ?nodeId=            // 深链优先，不发请求
2. 读 localStorage['roam.node']   // 上次用的，不发请求 —— 首帧就用它渲染
3. 都没有 / 已失效 → GET /api/broker/bootstrap
       → { nodes, recommended, prefs }         // Broker-local，不依赖 current node
4. 定下来才允许发第一条 /n/<id>/api/*
5. 异步 PUT /api/broker/preferences 同步「上次用的」，失败不阻塞
第 2 步的 localStorage 镜像不是优化，是必需品。项目在 AGENTS.md 「Preferences Arrive Late」 里已经写下这条账： 偏好是异步到的，任何用它做首帧的组件都会先拿到默认值。 当前机器要是走服务端偏好，用户每次刷新都会先看到另一台机器的项目列表、 半秒后整页跳变——比分隔条弹回去严重得多，因为那半秒里点下去的按钮作用在错的机器上。 所以：本地镜像定首帧，Broker 值只用于跨浏览器同步，且到达后若与本地不同， 只提示不自动切。

8. 认证：三段独立信任链

段凭证
用户 → Broker密码 + TOTP（复用 backend/auth），签发 ttmux_session cookie（HttpOnly / SameSite=Strict / 7 天）
节点 → Broker一次性 enrollment token 换长期节点凭证，落盘 ~/.roam/node.json；隧道全程 TLS（后续可上 mTLS）
Broker → 节点不带用户 cookie。节点认的是「这个请求是从已认证隧道里取出来的」——进程内 typed principal
永远不要用 header 判定「来自隧道」。 X-Forwarded-* / X-Roam-Internal 这类头，公网和局域网的任何客户端都能伪造， 而标准节点本机端口是照常对局域网开着的——一个伪造头就等于绕过登录。 PR #116 的 auth.WithInternal(r) 在 request context 上打进程内标记， 只有"已从可信隧道取出该请求"这条代码路径能设置它，线缆上不存在这个字段。
  • 本机监听端口始终进 public handler（要登录），隧道请求进 internal 入口。两条路不共用中间件链。
  • 审计日志里记 Broker 侧用户 + nodeId，否则多机之后"谁在哪台机器上删了什么"无从追。
  • Broker 掌握"哪个用户能访问哪些节点"的授权（近期单用户，为团队版预留）。

10. 传输协议选型：为什么是 WS + yamux，什么时候该换

「有没有标准协议 / 更省带宽的协议」这个问题要拆成两问： ①承载（把多条流塞进一条穿 NAT 的连接）用什么， ②每一路流量本身怎么编码（§11）。两者独立，别混谈—— 换承载省不了镜像的带宽，换编码也穿不了防火墙。

候选一览

方案标准穿透性多路复用队头阻塞结论
WebSocket + yamux
现在的选择		 WS 是 RFC 6455；yamux 不是标准（HashiCorp 库） 最好：443/wss 与普通 HTTPS 无异，企业代理放行有（yamux） 有（单条 TCP） P1 就用它。唯一能保证「哪都通」的组合，且已实现
HTTP/2 流 + 扩展 CONNECTRFC 9113 / RFC 8441好原生有（单条 TCP） H2 里只有客户端能发起流，Broker 无法反向开流进节点；要么 gRPC 双向流套一层、要么回到自定义帧——省不下 yamux 这层
HTTP/3 · QUICRFC 9000 / 9114中：UDP/443 可能被封，须保 TCP 回退原生 无 P3 的目标承载。三个真收益：无 HOL、连接迁移（手机切 Wi-Fi/5G 不断线）、0-RTT 重连
MASQUE（CONNECT-UDP / CONNECT-IP）RFC 9298 / 9484中原生（HTTP/3 之上）无 IETF 给「在 HTTP 上开隧道」的标准答案（iCloud 私密代理用的就是它）。但那是 L3/L4 隧道，我们要的是按 HTTP 请求路由到具体节点，用不上这层抽象
WebTransportW3C / over HTTP/3中原生（可靠流 + 不可靠数据报）无 浏览器侧的标准多路复用 API，镜像特别合适（丢帧走数据报，不排队）。Safari/iOS 尚未支持 → 必须留 WS 回退
WebRTC DataChannel / RTPRFC 8831 / 3550中（需 STUN，打不通要 TURN）有可选无序 已经在用（backend/p2p）。它的独门价值不是复用，是 P2P 直连绕开 Broker（§11）
SSH 远程转发RFC 4254中（22 端口常被封）有（channel）有 标准且成熟，但没有控制台、每台机器各配各的——正是我们要取代的散装用法
WireGuard 覆盖网
（Tailscale / Nebula）		非 IETF 标准但事实标准好（UDP 打洞 + DERP 中转）L3，不需要无 带宽最省，但用不了：浏览器不能当 WireGuard 端点。手机上打开网页就能用是本产品的前提，装客户端就废了这个前提
产品参照：frp 走 TCP + 可选 QUIC/KCP，复用用 yamux——和我们 P1 的选择一样； Cloudflare Tunnel 已经全面转 QUIC；ngrok 是 TCP 多路复用；Tailscale 是 WireGuard。 整个行业的路径都是「先 TCP+复用跑通，再迁 QUIC」，我们照着走就行，不必自研可靠 UDP。

P1 有一个必须现在就处理的坑：队头阻塞

今天浏览器对一台机器是四条独立 TCP（终端 WS、镜像 WS、P2P 信令 WS、REST）。 上了 Broker，它们全被塞进一条 yamux 隧道—— 一次 2GB 下载丢个包，TCP 重传会把终端一起卡住， 而这在今天是不会发生的（各走各的连接）。这是「加了多机之后单机体验反而变差」的典型退化。 

// 缓解：按流量性质开多条隧道连接，别指望一条扛所有（SSH 多路复用同思路）
tunnel[0] control   心跳 / ping / 注册            // 小、必须准时
tunnel[1] interactive 终端、REST、信令            // 小、要跟手
tunnel[2] bulk      文件下载 / 上传 / 镜像回退路径  // 大、可以慢
// 三条 wss 连接，各自一条 TCP；yamux 仍在每条之内复用同类请求。
// 换 QUIC 之后这个分层可以退化成一条连接 + 流优先级。

结论与迁移路径

  1. P1：WS + yamux 保持不变，但把它抽成 cluster/tunnel.Transport 接口 （Dial / Accept / OpenStream / Close）。今天只有一个实现， 换承载时不动 broker / node 的任何调用方。接口这一步现在就做，代价是零；等到 P3 再拆是几百行。
  2. P1：按上面三类开多条隧道，避免队头阻塞退化。
  3. P3：加 QUIC/WebTransport 实现，握手时协商（Alt-Svc 风格：先 WS 连上， Broker 告知支持 h3，节点下次优先 QUIC），失败自动回落 WS。
  4. 不做：自研可靠 UDP、L3 覆盖网、SSH 隧道。

11. 省带宽：四路流量各算各的账

Broker 通常是一台按流量计费的公网小主机。先把账算清楚再谈优化—— 省错地方等于没省：终端流量再压十倍，也抵不上镜像多开一分钟。

流量今天的实现量级（实测/估算）省法
浏览器镜像 CDP screencast → 整帧 JPEG over WS，六档自适应（browser/screencast.go 的 ladder：q28/960px 到 q90/4K） 4–8 Mbps（标清档 1280×800 q52 ~9fps）
超清档可到 20+ Mbps		 换视频编码：VP8/H.264 走 WebRTC video track。同画质 1–2 Mbps，省 5–10×。 帧间预测正好吃掉「屏幕大部分不变」这个特性，而整帧 JPEG 每帧都从零编一遍
手机镜像 adb exec-out screencap -p 出整屏 PNG 再转码 JPEG（phone/android.go） 同上，且设备端 CPU 也在烧（PNG 编码 + 传输 + 转码） 接 scrcpy 的路子：设备端 MediaCodec 直出 H.264，1–4 Mbps / 60fps， 手机 CPU 反而更低。这是全项目单笔最大的带宽收益

文件传输 HTTP 直传 / P2P DataChannel（p2p/download.ts + stream-saver） 与文件等大，没有压缩空间（多是已压缩格式） 唯一的解是不过 Broker：WebRTC P2P 直连（下方）+ Range 断点续传
REST / JSON 静态资源有预压缩 br/gz（server.go），API 响应没压 小，但 /git/graph、/search 这类能到几百 KB gin gzip 中间件 + ETag/If-None-Match。顺手就做
算一笔账：一路标清镜像 6 Mbps ≈ 2.7 GB/小时。每天看 8 小时 ≈ 21 GB， 一个月 640 GB——一台 1TB/月流量的小主机撑不住两个人。 换成 H.264 之后同样时长约 90 GB，再叠加 P2P 直连则趋近 0。 这不是"优化"，这是这套架构能不能付得起的问题。

P2P 直连：让大流量根本不进 Broker

信令走 Broker 隧道/n/<id>/api/p2p/signal
媒体 / 文件浏览器 ⇄ 节点 直连，不过 Broker
打不通时自动落回隧道中转（现有 relay 语义，侧栏 LinkStatus 已经会显示）
  • 仓库里已经有这套：backend/p2p/（ICE / UPnP / DataChannel）+ frontend/src/p2p/（PR #121）。 多机场景下它从"锦上添花"变成"付得起账单的前提"。
  • 这是相对「每台机器各配一条 frp」的真实优势：frp 的流量必然过中转机，我们能直连。
  • 两端都在 NAT 后时成功率取决于 STUN/UPnP；打不通就中转，用户只在 LinkStatus 上看到「中转」。 要不要自建 TURN 得等 P1/P2 把中转带宽实测出来再定，不要提前买。

还有三条几乎白捡的

  1. 页面不可见就停推流：document.visibilityState === 'hidden' 时暂停镜像帧 （切到别的标签页 / 手机锁屏）。今天的信用背压会让它自然降速，但不会归零—— 一个后台标签页可以持续烧几 Mbps。
  2. 切机器时断开旧机器的镜像：多机之后很容易同时挂着两台机器的镜像流而不自知。 规则：镜像流只跟当前机器，终端才是跨机器常驻的。
  3. 自适应初始档降一级：Broker 场景下的 RTT 天然比局域网高， 从「标清」起步会先冲高再回落，白烧一段。跨 Broker 时初始档改「流畅」。

12. Broker 扇出：搜索与工作台

有两件事天然横跨所有机器，它们也是多机之后仅有的「功能变强」而不只是「能切换」的地方： ①搜索——只搜当前机器等于把「那东西在哪台机器上」这个路由工作推回给人； ②工作台顶上的「需要你」行动队列——它回答「我下一步做什么」，而"下一步"不该被机器边界切开。 两者共用同一套扇出机制，一起进 P1。而且搜索反过来约束数据形状（见下 ③），晚做就是全面返工。

#186 刚好把工作台的扇出从"不可行"变成了"一台一条"。 合并前，概览页对最多 14 个会话逐个打 /claude /codex /capture， 6 秒一轮、峰值 42 条请求——乘以 N 台机器根本不用谈。#186 把这些字段并进 /projects 一条请求（top[] 2→3、runningAgentSessions 由 bool 放宽成 claude|codex、判 waiting 时带出尾行当摘要），前端那套轮询整段删除。 于是跨机器工作台 = N 条请求 6 秒一轮，十台机器也才十条。 这不是巧合能一直有的运气——以后再往首页加数据，都得先问一句"乘以 N 台还成立吗"。 
// Broker 扇出：一条请求打散成 N 条，逐台流式回推（NDJSON / SSE）
GET /api/broker/search?q=train&limit=20&scope=all
  ├─ /n/n_01/api/search?q=train&limit=20   → 12ms  9 条   // 节点侧零改动
  ├─ /n/n_02/api/search?q=train&limit=20   → 45ms  3 条
  ├─ /n/n_03/api/search?q=train&limit=20   → 210ms 5 条
  └─ n_04 离线 → 跳过，结果里留一条 {"node":"n_04","error":"offline"}

// 响应是一行一批，到一批推一批：
{"node":"n_01","hits":[…],"tookMs":12,"indexing":false}
{"node":"n_02","hits":[…],"tookMs":45}
{"node":"n_03","hits":[…],"tookMs":210,"truncated":true}
{"done":true,"nodes":4,"failed":["n_04"]}

// 工作台同一套：一台一条，节点侧还是那个 /projects，一个字段都不用加
GET /api/broker/projects?scope=needs        // 6s 一轮
  └─ /n/<id>/api/projects × N → 前端把各台的 buildNeedCards() 结果 concat 后按同一优先级排
// 注意 scope=needs：项目墙只要当前机器那一台（项目是一台机器上的一份 checkout，
// 混在一面墙上同名仓库会出现四次）。扇出只为顶上那层行动队列和活动轨。
设计点做法与理由
① 必须增量返回 等最慢的节点 = 每次按键都等最慢的那台。一台 210ms 的云机器会让本机的 12ms 结果也变成 210ms。 前端本来就是「本地条目先出、后端结果并进来」的模式（useSearchResults.ts）， 扇出只是把「后端」变成"多个后端逐个到"，UI 心智不变
② 不给远端降权 别用 score × 0.7 压别台机器的结果——「我明知道那个文件在 GPU 机上」的搜索 会永远排在本机噪音后面。改成按机器分组：本机组在最前，其他机器各一组。 顺序上偏向本机，分数上不动它
③ id 必须带 nodeId 最容易漏 shell/palette/rows.ts 的 dedupeByKey 按 kind + id 去重，而 SearchHit.id 今天是 「会话名 / 文件绝对路径」。两台机器上都有 build、都有 ~/codes/roam/README.md —— 不带 nodeId 就会被静默合成一条。 action.target 同理（打开 = 切机器 + 打开）。与 §6 的 TermKey 同一笔账
④ 部分失败要显式 超时/离线的机器在结果里留一行「树莓派 未响应」。静默丢弃比搜不到更糟—— 用户会据此认定"那台机器上没有"，然后去别处找半天
⑤ 超时与并发 名字搜索每节点硬超时 1.5s，内容搜索 8s；Broker 侧扇出并发上限 8， 20 台机器分批走。离线节点直接跳过不占并发
⑥ 内容搜索另算 /search/content 走 rg，比名字搜索贵一到两个数量级。 名字搜索默认全机器，内容搜索默认只本机 + 一枚显式的「在全部机器里搜」。 扇出 20 台 = 同时点着 20 个 rg，那是能把所有开发机一起拖慢的操作
⑦ 索引状态 per-node 节点各自建自己的文件索引（indexing 标志今天就有）。 UI 要能说「3 台里 1 台还在建索引，这批结果可能不全」，而不是笼统一句
⑧ 带宽 结果是小 JSON，扇出对带宽无压力（这是少数不用担心 §11 那笔账的地方）。 压力在各节点 CPU 和 Broker 的扇出并发上
⑨ 一个是轮询，一个是按键触发 两者节奏完全不同：搜索一次性、可取消；工作台 6 秒一轮、常驻。 所以工作台的扇出要错峰（各节点请求打散在这 6 秒里，别每 6 秒同时打 N 条） 并且页面不可见就停——否则一个后台标签页会持续拨十台机器。 离线节点直接跳过，不要每轮都去撞一次
⑩ 队列不按机器分组 与搜索刚好相反。搜索是「我在找东西」，分组帮你缩范围； 队列是「帮我排序」，按机器分组会把最急的那件推到第二组去。 队列只按优先级排（等待输入 > 蜂群待解锁 > 待收尾），机器身份靠卡片上的方章表达

前端落点：search/client.ts 的 searchAll 从「一次 fetch 拿 JSON」 改成「读一条流、每行 setState 一次」；search/types.ts 的 SearchHit 加 nodeId 并把它并进 id；shell/palette/rows.ts 的 mergeRows 加机器分组。节点侧后端一行不改——它只是被并发调用了 N 次。 工作台这边落在 project-list/needs-queue.tsx：buildNeedCards() 已经是纯函数（projects[] + swarms[] → 卡片数组），跨机器就是对每台各调一次再 concat， 卡片的 key 补 nodeId。activity-rail.tsx 同理。

13. 版本偏斜：控制台来自 Broker，API 来自节点

这是这套架构独有的新问题，单机时代不存在：浏览器加载的前端是 Broker 上那一份，但它调用的 API 在各台节点上，而节点是用户各自升级的。 一台没升级的节点 + 新前端 = 报错，而且报在业务页面上，用户会以为是那台机器坏了。
  • 节点注册时上报 version 与 capabilities（PR #116 已经在报）。
  • Broker 记录自己的前端版本；不兼容时 /nodes 卡片给黄字「{version} 可升级」， 切到该节点时页头芯片转黄——不阻断，因为大部分接口是兼容的。
  • 真正的破坏性变更要靠 capabilities 声明能力而不是比版本号： 前端按能力隐藏入口（老节点没有 swarm 就不显示蜂群页），这比版本区间判断稳。
  • 升级路径：/nodes 卡片上给一键「升级命令」（同接入命令，复制到那台机器执行）。

18. 未决

  1. Broker 部署形态：独立公网小主机（推荐，职责干净）还是和某台标准节点同机？ 同机部署要注意那台机器既是 Broker 又是节点，/n/<自己>/ 会绕一圈隧道回到本机—— 要不要短路成直接调用（省一跳，但两条代码路径）。
  2. install.sh 的分发：Broker 要不要顺带托管二进制？不托管则节点得能访问 GitHub Release， 而"公司内网机器上不了外网"恰恰是这套方案的典型用户。倾向：Broker 托管， 它本来就有一份同版本二进制。
  3. enrollment 有效期：10 分钟够不够？跨时区手动粘贴命令的场景可能要 24 小时。
  4. 多用户是否纳入近期范围，还是先"单用户管多机"、团队版后置。
  5. 扇出规模：并发 8 / 超时 1.5s 是拍的，等真有 10+ 台机器再按实测调。 另一个没定的是「机器很多时要不要按分组缩小搜索范围」——20 台全搜可能大部分是噪音。
  6. TURN 要不要自建：P2P 打不通时的中转。先在 P1/P2 把实际中转流量测出来再决定—— 自建 TURN 的带宽账和 Broker 中转是同一笔，提前买没意义。
  7. 镜像换视频编码的落点：浏览器侧 CDP 只给 JPEG，要么在节点上把 JPEG 序列再编码（多一次转码，省带宽但费 CPU）， 要么改用 Page.startScreencast 之外的路子（如 chrome --remote-debugging + WebRTC getDisplayMedia）。 手机侧则清晰得多：scrcpy 的做法是设备端 MediaCodec 直出，不需要转码。
